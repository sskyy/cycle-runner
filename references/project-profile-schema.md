# 项目画像规范

项目画像固定存放在：

```text
docs/agent-project-profile.md
```

项目画像记录执行任务所需的项目背景、工程原则和调查入口。生成循环任务文件时，必须把该文件全文逐字复制到任务文件中，不得只写路径、摘要或链接。

这样处理有两个目的：

1. 每个任务文件都保留生成时的完整项目背景。
2. 任务目录移出仓库归档后，仍可独立还原当时适用的目标和工程约束。

项目画像不应包含循环任务协议本身。立项轮次、圈数上限、里程碑状态、评审流程、人工白名单属于 `protocol-template.md`；任务级的价值判断属于任务文件。

## 必需内容

### 1. 项目定位

- 项目解决的问题和主要使用者。
- 当前架构的基本方向。
- 权威工程规则的名称和路径。

项目画像应直接写明执行任务时必须理解的核心背景，不能只列出若干文档路径而不说明项目。

### 2. 功能目标

- 项目的长期产品目标。
- 重要业务概念的定义。
- 明确的非目标或范围边界。

### 3. 技术目标

- 架构质量目标。
- 性能、可靠性、安全性、兼容性等重要约束。
- 当前开发阶段对迁移、兼容和数据保留的态度。

### 4. 代码职责

- 主要目录和组件的职责。
- 通用基础设施与业务代码的边界。
- 不允许出现的依赖方向或代码放置方式。

### 5. 编码与修改原则

- 根因修复要求。
- 生成文件和源文件的关系。
- 配置读取方式。
- 数据模型、时间单位、错误处理等项目特定规则。
- 变更后需要重新生成或重新启动的内容。

### 6. 调研入口

使用简洁列表说明：

- 权威规范。
- 主要源码入口。
- 相关测试目录。
- 运行日志、数据库或外部系统的调查入口。
- 与常见任务类型对应的专项参考。

路径用于帮助定位，但画像必须同时说明每个入口的用途。

### 7. 测试与运行环境

- 项目标准测试命令。
- 不同测试层级的使用范围。
- 本地服务、容器、数据库或浏览器环境的必要说明。
- 测试资源的准入条件、排队入口与超时语义（若存在）；记录项目机制，不复制模板的等待、计数与交接规则。
- 可作为 A 类验收契约的既有可执行门禁（测试 lane、旅程、合同测试、结构检查）的清单位置与运行方式。
- 如何处理任务开始前已经存在的失败。

已有失败应由具体任务在开始时实际运行并记录基线，不应在项目画像中维护只允许人工修改的长期白名单。

## 可选内容

### 缺陷复盘协议

项目已有缺陷复盘流程时，在画像中写明：

- 根因机制词表的权威位置（封闭词表）；
- 逃逸类别的细分（如有）；
- 逃逸证明的工具或命令；
- 语义性质抽样策略的项目默认值（样本量、种子、通过标准；如有，供 Task 价值判断引用）；
- 主干既有缺陷的登记流程与位置；
- 范围外缺陷（协议模板「缺陷复盘」第 8 条）的登记方式：缺陷条目、仍失败检查的 owner 与期限、后续 issue 的建立流程；
- 复发机制的治理方式，例如建立治理 issue。

循环任务的审计按这些内容执行协议模板中的「缺陷复盘」；未写明时使用模板的默认机制词表和方法。画像只引用项目的权威位置并说明用途，不复制词表内容。

## 不应写入项目画像的内容

以下内容由循环协议统一规定，不得在项目画像中重复：

- 设计或实现循环的轮次预算。
- 评审和裁决的步骤。
- 里程碑状态机。
- 固定数量的风险实验要求。
- 通用断言库、负向夹具或证据 schema 要求。
- 只允许人工修改的测试白名单或隔离基线。
- 旧任务的运行状态、评审结论或实现计划。

项目确有特殊要求时，应陈述业务或技术原因，而不是复制一套项目专用循环协议。

## 写作要求

- 使用正式、准确、容易理解的语言。
- 重要结论应说明原因；避免只有口号而没有适用范围。
- 项目事实与当前仓库一致。
- 同一规则只在一个权威位置完整定义。
- 不使用难以理解的缩写；无法避免时首次出现应给出完整名称。
- 不记录短期任务进度。

## 缺少画像时的调查顺序

1. `AGENTS.md`、`CLAUDE.md`、README 和项目规则。
2. 架构设计、产品计划和 ADR。
3. 包管理文件中的脚本与测试命令。
4. 主要源码目录和组件入口。
5. CI 配置、测试配置和开发环境说明。
6. 与当前需求相近的正式设计文档；旧循环任务归档只供人工复盘，不应作为新任务设计输入。

首次建立画像后，默认交给用户确认。用户明确要求连续执行时，可以在完成自检后直接生成任务文件。
