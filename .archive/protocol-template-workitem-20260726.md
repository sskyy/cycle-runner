### 设计文档规范
方案文档同时服务两个收敛循环：设计循环（additional task 1 评审轮 / additional task 2 裁决轮）与实现循环（additional task 3 实现轮 / additional task 4 审计轮）。文档头部四个固定小节是实现循环的唯一共享状态载体，全部采用覆盖式维护，头部不得出现四小节之外的进度叙述。

**一、头部固定小节（依次四个）**
1. **进度账本**：第一行记录轮次计数 `round: k/N`（N 为实现循环轮次预算，初始化为 20）。第二行记录下一轮计划 `next: <一句话目标> | 预期效果: <可观测变化>`，规则如下：单行、覆盖式维护，任一时刻只存在一份活的计划（禁止写入 Backlog——Backlog 按定义不触发循环，计划写在那里等于没有约束力）；目标必须**可证伪**，即写明预期的可观测变化（例如某条从未执行过的门禁变为可执行、追溯矩阵中哪些行获得覆盖、某项环境设施从缺失变为具备）；选择目标时必须优先「能解锁最大剩余范围的步骤」，而非「边际成本最低的下一个增量」——尤其当某条门禁从未真正执行过时，让它可执行优先于在已可执行的门禁上继续加固。实现轮与审计轮在各自结束前都必须覆盖式改写该字段，审计轮并须核对上一轮的 `next` 是否兑现（见 additional task 4）。依据：一次运行 77 轮的实现循环，审计轮每轮都把「下一轮该做什么」写进 Backlog（累计 48 条），其中 Audit41–Audit56 十余轮的计划几乎逐字相同，而该计划直到第 72 轮才被执行——计划一直正确、一直被记录、一直没有约束力，且没有任何环节回头核对它是否被执行。其余内容为工作项列表，初始化时将实施范围分解为状态为 `open` 的工作项。每个工作项字段：稳定 ID（`W-01` 起，分配后不得重编号或复用）、状态（`open` / `closed` / `reopened` / `disputed`）、声明（不超过两句，细节通过规范性条款 ID 引用）、证据引用（门禁命令 + 用例文件或合同标识）、开启/关闭轮次、复开计数。状态迁移约束：置为 `closed` 必须同时挂接满足完成纪律的可复跑证据引用；`closed` 置回 `reopened` 必须附复跑失败记录；复开计数达到 2 的工作项一律置为 `disputed`。工作项只允许状态迁移，不允许删除。
2. **完成纪律**：实现循环的收敛判据（门禁集合）。每条条目必须包含四个字段：(a) 适用的声明或变更类型，引用规范性条款 ID 或注明规范出处；(b) 可复跑的门禁命令或可机检产物；(c) 无效证据界定——以失效类别表述（例如：测试环境无法暴露目标缺陷、断言未覆盖过程不变量、绕过生产代码路径），示例仅可基于已实证的缺陷新增，禁止投机性枚举；(d) 执行策略，取值为 `每轮必跑`（快速门禁）或 `按关联声明触发`（重量级门禁，下称触发式门禁）。无法给出可复跑判定方式的表述不得作为纪律条目。条目来源：设计文档中的全部关键声明（经追溯矩阵保证覆盖），以及项目内既有工程规范与测试规范（项目画像中的权威规范文档、完成纪律种子、历轮 review 沉淀的不变量等，条目中注明出处）。变更协议：条目只增不减、只紧不松；循环内新增或收紧须注明轮次与动因（引用裁决记录 ID 或审计发现）；放宽或删除条目仅允许人工执行。
   **条目正文只承载上述四个字段，必覆盖项清单必须外移**：门禁的必覆盖项、断言对象、mutation 方向、里程碑归属一律**不写在设计文档内**，改落在任务文档目录下的 `{{DOC_DIR}}/gates/<门禁 ID>.testlist.md`——一条必覆盖项一行，字段为：稳定编号（`<门禁 ID>-T01` 起，不复用）、断言对象、会使其失败的 mutation 方向、归属工作项、新增轮次与动因；设计文档的纪律条目只按 `<门禁 ID>-Tnn` 引用。理由：必覆盖项实质是测试规格，用散文维护时没有任何执行器可校验、只能靠人反复读，是设计循环最大的缺陷源（经验依据：一次运行 21 轮的设计循环，59 条 p1 中 38 条出自门禁散文，两条纪律条目各自膨胀到近万字符）；外移后实现循环第一轮即把 testlist 转成 `it.todo` 骨架，此后由测试框架而非评审者维护。**单条纪律条目正文超过 1500 字符即为结构违规。** 既有条目的迁移不要求单轮完成：裁决轮每次触及某条纪律时，必须把该条的必覆盖项整体外移到其 testlist 后再做本轮修改（一次一条，禁止一轮内做大规模整体重写）。testlist 与设计文档同受本变更协议约束，其新增/收紧同样注明轮次与动因。
   **门禁债务（gate debt）**：设计循环识别出的「判定强度不足」类缺陷（审查维度 5 第二类），若裁决轮无法在本轮给出确定的加强方式（典型情形是强度只有跑起来才能判定），必须登记为门禁债务，而不是留在阻塞集里逐轮论证、也不是当作已解决。登记形态为该纪律条目正文**开头**的一行标记：`【门禁债务 D-01｜缺陷摘要（一句）｜登记轮次｜解除条件】`，`D-01` 起顺序编号、稳定且不复用；解除条件必须写成可判定的动作（默认形态是"补齐该判定并按其 mutation 方向做一次 mutation check 且留记录"）。同时在进度账本登记一条对应工作项。**效力（不得弱化）**：债务未按解除条件清除前，**以该纪律条目为证据引用的任何工作项一律不得置为 closed**，实现轮与审计轮都按此判定；债务只能由实现循环按解除条件清除，放宽或删除债务仅允许人工执行。`【】` 是设计文档保留给门禁债务的唯一标记，不得他用。
3. **Backlog**：非阻塞的改进建议与纪律/规范变更提议，只进不出，不触发循环轮次，等待人工处置。**可表述为「凡 X 必须 Y」的通用规则禁止登记于此**——它们必须在识别当轮由裁决轮按「模式清扫义务」（见 additional task 2）在全文扫清，并在可机检时并入机检门禁；Backlog 只承载需要人工决策的取舍、跨任务提议与无法机械扫描的观察。依据：一次运行 21 轮的设计循环，其 Backlog 有 76/104 条自标「同族 / 同型 / 收紧形态」，即同一规则被登记后在别处反复复发，每次复发消耗一整轮循环。**「下一轮应该做什么」同样禁止登记于此**——它属于头部 `next` 字段（见本节第 1 条），写进 Backlog 即视为结构违规。
4. **争议项**：复开计数达到 2 的工作项，以及复提计数达到 2 的评审主张。记录冻结原因与双方论点摘要，供人工仲裁；循环双方不得再修改对应条目，其存在不阻塞循环终止。

**二、正文结构（依次）**
1. 背景与现状：每条现状断言附代码锚点（文件路径或符号）；未经亲自验证的内容不得陈述为事实。
2. 目标 / 非目标。
3. 决策记录（decision record）：每个关键决策记录唯一结论，以及被否选项与否因（各一至两句）。方案只保留一个；否因用于避免后续评审重复论证已完成的取舍。
4. 规范性条款（normative clauses）：全部设计约束的唯一权威定义处。逐条编号（`C-01` 起，稳定且不复用），每条原子、单一陈述、可验证，使用统一约束词（必须 / 禁止 / 应当 / 可以）。条款之外的文字均为资料性说明（informative），与条款冲突时以条款为准。
5. 术语与键名表：canonical 术语、标识符、键名的唯一出处。
6. 追溯矩阵（traceability matrix）：规范性条款 ↔ 工作项 ↔ 完成纪律条目 ↔ 验收项的映射表，用于机械检查覆盖缺口。
7. 风险与验收：仅引用条款 ID，不复述条款内容。

**三、写作规则**
1. 单一事实源（single source of truth）：任何约束仅在其规范性条款处完整陈述一次；工作项、纪律条目、验收、风险等位置只引用条款 ID。同一约束的重复陈述视为结构违规。
2. 不得引用 review 文档中的 finding 编号（review 文档每轮清空）；跨轮动因一律引用裁决记录中的稳定 ID。
3. 文档中不保留评审与修订叙事；修订历史只存在于裁决记录。

**四、入口自检**：初稿完成或每轮修订完成后必须执行，违规先修复再交付：
1. 结构检查（机械可检）：四小节齐全且字段完整；条款与工作项 ID 唯一；文档内引用全部可解析（含向 `gates/*.testlist.md` 的 `<门禁 ID>-Tnn` 引用与其反向可解析性）；无重复陈述；追溯矩阵覆盖全部规范性条款，关键声明均有完成纪律条目覆盖；每条 `【门禁债务 D-xx】` 标记字段齐全（摘要 / 登记轮次 / 解除条件）、ID 唯一不复用，且在进度账本有对应工作项；单条完成纪律条目正文 ≤ 1500 字符（不含门禁债务标记行；超出即说明必覆盖项未按规定外移。本规范在既有任务中途启用时，启用前既有的条目在被裁决轮首次触及并完成外移之前豁免本项，豁免清单记在覆盖账本、只减不增——否则本项在启用当轮就会把全部既有条目判为结构违规，复现"门禁起点即红"的失效形态）。
2. 语义自检：按「评审与裁决协议」的审查维度自查一遍。


### 评审与裁决协议
设计循环由 additional task 1（评审轮）与 additional task 2（裁决轮）交替执行，直至收敛。共享定义如下：

**审查维度**：
1. 致命设计错误（按原文实施会造成难以挽回的方向性错误）；
2. 违背上面的代码职责；
3. 违背上面的功能目标和技术目标；
4. 违背「设计文档规范」；
5. 完成纪律质量缺陷，分两类，severity 同级但**阻塞位不同**：
  - **覆盖缺口**——关键声明没有任何纪律条目 / testlist 项覆盖。可机械判定、集合有限（追溯矩阵即可穷举），属设计循环的正常阻塞项，按常规裁决修复。
  - **判定强度不足**——判定强度与声明类型不匹配（例如并发/竞态类声明的门禁运行在无法暴露真实交错的环境中）。这一类受下方「门禁质量 finding 的证据门槛」约束，且其最终证明方式是实现循环的 mutation check 而非评审论证；未能在设计循环内修复者按「门禁债务」机制处置（见「设计文档规范」一.2）——**不阻塞设计循环终止，但阻塞实现循环中以该门禁为证据引用的一切工作项关闭**。这不是降级：判定强度的要求分毫未松，只是把它移到唯一能真正证明它的时点上，并且移到它真正起作用的位置上（工作项关闭前，而非设计定稿前）。

**finding 纪律**：每条 finding 必须包含五个字段：位置锚点（条款 ID 或小节）；被违反的依据（任务要求 / 附文件路径的代码事实 / 目标 / 规范条款）；证据；建议修正；修复验证标准（说明如何确认已修复）。字段不全的 finding 最高定为 p3。

**门禁质量 finding 的证据门槛**（审查维度 5「判定强度不足」一类专用）：要定为 p1，其证据字段必须至少给出下列一项**实证**——(a) 实跑该门禁命令并附输出（证明它当前即红，或它对某个已知缺陷判绿）；(b) 给出一个该门禁会放过的**具体错误实现样例**（代码片段，或可复现到行为层面的实现描述）；(c) 指出该门禁的**执行环境**在结构上不可能暴露该声明类型的缺陷（如并发/竞态声明跑在单连接 / 单进程 lane），并附环境事实的代码锚点。三项都给不出的论证式主张最高定为 p2，写入 Backlog 或按门禁债务登记，不进阻塞集。依据：一次运行 21 轮的设计循环中，38 条门禁类 p1 有 35 条为纯论证、零实证，而唯二附了实跑输出的两条当场坐实了两个自第 1 轮起就存在、却二十轮无人发现的门禁失效。

**severity 分级**（按后果分级，是设计循环的循环判据，不得自创等级或改变语义）：
- p0：致命错误，修正需要重构文档主干；
- p1：实施前必须修正的设计缺陷——按原文实施会走错方向或产生返工（含完成纪律质量缺陷；其中「判定强度不足」一类的 severity 不降，但阻塞位按审查维度 5 落在实现循环侧，见「门禁债务」）；
- p2：局部正确性缺陷——表述错误、引用错误、边界遗漏等，修复可依据该 finding 的修复验证标准直接确认；
- p3：非阻塞的建议或观察。

结构违规（四小节缺失、字段不全、ID 冲突、引用悬空、重复陈述等机械可检项）不参与分级，单列清单，由裁决轮无条件修复。

**裁决记录（adjudication log）**：与设计文档同目录的持久文件，命名为设计文档名 + `-adjudication.md`，append-only，仅由裁决轮写入，首轮由裁决轮创建。头部维护 `design-round: j/N`（j 为累计评审轮计数，N 为设计循环轮次预算，初始化为 5；本规范在既有循环中途启用时，改记 `budget-remaining: k` 并自启用时初始化，每轮裁决减一）。每轮追加：本轮修改的条款 ID 列表；本轮是否为**自激轮**的判定（定义见下「循环预算与停滞判据」）；逐条裁决记录，字段为稳定 ID（`Rj-Fxx`）、主张摘要（一句）、位置锚点、裁决（采纳 / 驳回 / 部分采纳 / 因重写失效）、证据或理由、修改落点条款 ID、复提计数（re-raise count）。该文件是设计循环唯一的跨轮记忆：驳回理由、复提追踪、修改范围均以它为准。

**循环预算与停滞判据**（由裁决轮在终止判定前评估，其结论优先于 additional task 2 第 10 条的其余分支）：
- **轮次预算**：设计循环轮次预算耗尽时循环终止，把未决的 p0/p1 连同其锚点写入设计文档「争议项」，转人工，不再启动新 chat。
- **自激判据**：某轮的全部 p1 若都锚定在**前两轮**裁决记录「本轮修改的条款 / 位置」清单之内，该轮记为**自激轮**（裁决记录中显式标注，附锚点与清单的交集）；**连续两个自激轮即终止循环**，理由写入裁决记录，转人工。依据：自激轮说明循环正在消化自己上一轮产生的文本，而不是在暴露初稿的存量缺陷——一次运行 21 轮的设计循环，自第 6 轮起平均约八成的 finding 锚定在前两轮新写的文本上（多轮达 100%），继续迭代的边际收益为负。
- 两种终止都按 additional task 2 第 10 条的收敛分支收尾（整理 Backlog、执行 `afplay`），不启动新 chat。

**任务文档目录**：设计文档、review、裁决记录、覆盖账本（`{{SLUG}}-review-coverage.md`）、门禁 testlist（`gates/<门禁 ID>.testlist.md`），以及执行过程中的非代码产物（证据、mutation 记录、补丁草稿等），一律落在 `{{DOC_DIR}}/`。
