### 共同原则

1. **产品结果优先**：下列规范用于促进任务完成，不得为了完善流程文件而延迟主要工作。
2. **证据优先**：涉及代码现状、运行行为或外部接口的判断，应优先使用源码、现有测试、实际命令或最小验证实验。纯逻辑矛盾可以使用准确引用和具体反例证明。
3. **一次处理同类问题**：评审问题必须说明根因和检查范围，并列出该范围内全部同类问题。裁决或修复时应再次检查同类位置并一次处理完毕。
4. **设计不追求完美**：设计阶段只消除会使实施方向失效、目标受损或里程碑不可执行的问题。验证程序仍可加强、局部表述可改善等事项不得单独延长设计循环。
5. **验证采用项目原有体系**：优先使用项目已有测试、合同、运行脚本和真实环境。只有任务确有需要时才增加专用验证程序。
6. **协议版本固定**：本次运行始终使用本文件中的规则，不得在运行中同步其它版本。
7. **会话自主性**：设计、评审、实现和审计分别在独立会话中完成。各会话不得向用户询问如何继续；遇到未明确规定的事项，应依据任务目标、项目原则和已取得的证据作出合理决定，并记录理由。


计数规则：

- `d` 由设计裁决轮增加，设计评审轮不增加。
- `k` 由实现轮增加，审计轮不增加。
- `r` 是当前里程碑因实现缺陷从 `待审`退回`开放`的累计次数；验证缺口直接加强后产品仍正确、或里程碑本来就是`开放`时不增加。

- `开放`：尚未完成。
- `待审`：实现轮已取得通过证据，等待独立审计。
- `已完成`：审计轮独立复验通过。

实现轮不得将里程碑标记为 `已完成`。

#### Reopen、缺陷复盘与收敛

设计文档中每个里程碑还必须维护 `reopen-count` 与 `defect-mechanisms`：

- `reopen-count`：审计确认实现缺陷并把该里程碑从`待审`退回`开放`的次数。纯验证缺口、原本就是`开放`的里程碑不计。
- `defect-mechanisms`：以「根因机制·模块」为键的计数。审计轮每确认一个实现缺陷，就为它的键加 1（同一审计轮同一个键只加一次），不论里程碑原本是`待审`还是`开放`。机制只能取「缺陷复盘」中的机制词表；模块写项目的规范模块根。可以附简短说明，说明不参与计数，也不得通过改写说明或改换模块写法规避升级。

旧任务首次采用本机制且缺少计数时，下一审计轮根据 `retro.md` 中该里程碑真实的审计记录初始化。

触发规则：

- 某个「机制·模块」计数达到 2：`convergence-mode: domain-review`，对该机制执行完整复盘。
- 同一里程碑 `reopen-count` 达到 3：`convergence-mode: milestone-review`，对该里程碑出现过的每个机制执行完整复盘。
- `milestone-review` 优先级更高；收敛模式一旦触发，直到里程碑关闭前不得恢复为 `normal`。之后又有机制计数达到 2 时，同样对它执行完整复盘。

触发收敛模式的审计轮必须在当前实现审计文件顶部维护 `## Convergence Note`，不得新增流程文件。Note 只记录尚未闭合的差异，不复制 Task、设计正文或完整历史，并固定为四部分：

1. **Remaining closure map**：未闭合的「机制·模块」、对应缺陷卡片的摘要及当前失败证据。
2. **Root cause and scope**：完整复盘的结果：逃逸证明、逃逸类别、来自权威来源的同类普查，以及前轮为何漏检。
3. **Next implementation batch**：按依赖顺序写出下一轮必须达成的结果：要成立的不变量与结构性质、输入范围与判定标准、完成条件。只写要达成什么，不写实现方案（见「缺陷复盘」第 5 条）。
4. **Closure gates**：当前应红、完成应绿以及不得退化的命令，包括结构性质的机检命令与缺陷注入方法。

后续审计覆盖写审计文件时必须保留并更新该 Note，直到里程碑关闭。`next-action` 应简短指向 Note 的下一实施批次；`retro.md` 记录 reopen 次数、各「机制·模块」计数、收敛模式、完成的结构性修改及关闭轮次。

#### 缺陷复盘

审计确认的每个实现缺陷都按以下方法复盘。项目画像给出「缺陷复盘协议」（机制词表、逃逸类别细分、逃逸证明工具、主干既有缺陷的登记流程）时，使用项目画像中的词表与工具；没有给出时使用本节的默认词表和方法。

1. **缺陷卡片**：每个实现缺陷在审计文件中写明现象、证据、根因机制与模块、在任务基线 revision 上能否复现、逃逸证明、逃逸类别、同类普查和补救。
2. **逃逸证明**：在缺陷修复前的代码上运行实现轮声称通过的验收命令，以及离缺陷最近的既有测试，记录结果属于哪一种：未执行、执行但看不到失败、失败但被忽略、不存在相关测试。
3. **逃逸类别与补救**：
   - **A 验证体系缺陷**：相关验证没有执行、被跳过、判定条件看不到失败，或替身、夹具与真实实现不一致。补救是修复验证机制本身（接线、取消跳过、修正判定条件并加正向对照、替换失真的替身），不只是增加一个用例。
   - **B 用例不足**：验证机制正常，但缺少维度或实例。补救是从权威来源（注册表、生成物、状态机、类型定义或可执行的普查）列出全部同类实例，并扩展模型、参考函数或输入生成器；只有确实没有可用模型时才补充单个用例，并写明理由。
   - **C 其他**：设计没有定义该行为、缺陷位于第三方或框架等。写明需要的设计裁决或上游修复。
4. **完整复盘与结构性修改**：某个机制触发收敛时，对它的全部缺陷执行逃逸证明与同类普查，并要求下一实施批次做出使该机制在结构上不能再发生的修改，例如一个事实只有一个写者或读者、从权威来源派生、类型化的载体、统一的参考函数。结构由实现轮设计，并同步修订设计文档中对应的方案。审计按三项验收：结构性质可以机检（类型、模块边界，或列举全部写者与读者的契约测试）；人为加回第二条路径（第二个写者或读者、手写副本、未类型化的字段）时测试变红；逃逸类别要求的验证补救已经完成。结构完成之前，同一机制的新实例照常认定为实现缺陷。
5. **审计只写要达成什么**：审计可以用候选修改验证可行性，但候选修改不属于实施批次；实现轮自行设计实现，与审计的可行性验证不同时说明理由。
6. **主干既有缺陷**：在任务基线 revision 上能复现的缺陷不是本任务引入的。除了在本任务中修复，还按项目画像的缺陷复盘协议登记；画像没有规定时，在 `retro.md` 中单独列出。本任务引入的缺陷只记录在审计文件中。
7. **超出任务范围的修改**：结构性修改需要 Task 明确排除的改动（例如 Task 规定不改的协议或框架）时，按 C 类写明需要的裁决或上游修复，并按项目的 issue 规则建立后续任务。该缺陷若违反 Task 要求或里程碑验收，里程碑仍不能关闭。

### 设计文档要求

设计文档应包含：

1. **背景和现状**：只写与任务有关的事实，并给出代码、文档或运行证据。
2. **目标与非目标**：逐项对应 Task 的编号要求。
3. **方案**：只保留一个明确方案，说明关键决策及理由。
4. **里程碑**：按依赖顺序编号为 `M-01..M-N`。
5. **风险与验证安排**：区分设计期必须验证的风险和可以在实现期验证的风险。
6. **基线**：记录任务开始时的 Git revision、工作树状态，以及与本任务相关的已有测试结果。

每个里程碑必须包含：

- 可独立观察的结果。
- 覆盖的 Task 要求编号。
- 前置里程碑。
- `reopen-count` 与 `defect-mechanisms`，初始分别为 `0` 与空集合。
- 验收命令；如果命令尚不存在，应准确说明实现阶段需要新增的测试或运行入口。
- 最新证据。

里程碑应当是可以运行和验证的阶段性系统状态。第一个里程碑应尽早消除最大的技术不确定性；对于跨组件任务，通常应建立最小端到端链路。

设计阶段采用精简的可执行验收：

- 每个里程碑至少有一个可执行验收入口或明确的待建测试。
- 并发、崩溃、切换、删除、权限和不可逆数据变更等高风险行为，至少提供一个能区分错误实现的负向对照或最小验证实验。
- 不要求为每个断言建立专用 schema、夹具集合或通用断言框架。

### 设计复审条件

只有以下六类问题可以要求下一轮设计评审：

1. **关键事实错误**：方案依赖的技术、接口、代码行为或运行条件与实际不符，可能使方案整体失效。
2. **内部逻辑矛盾**：两项要求不能同时满足、关键路径不可达，或里程碑按设计无法通过验收。
3. **违反项目原则**：方案违反项目权威规则中的架构职责、数据原则或工程约束。
4. **违反任务目标**：方案偏离 Task 的目标、范围或硬性约束。
5. **里程碑不可执行**：里程碑过大、依赖顺序错误、验收不明确，或明显不能在合理实现轮次内完成。
6. **必须提前验证的重大风险**：该风险无法在实现环境中及时验证，若推迟会使后续实现整体失效。

验证还可以更严格、测试还可以增加、资料性说明可以改进、局部命名可以优化等问题，均不得单独触发下一轮设计评审。

若同一设计领域第二次出现需要复审的问题，裁决轮不得继续逐句补充说明。应根据问题性质，将完整行为整理为状态表、真值表、参考函数、结构化清单或最小契约测试，并一次检查全部输入情况。
