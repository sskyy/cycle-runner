### 共同原则

1. **产品结果优先**：下列规范用于促进任务完成，不得为了完善流程文件而延迟主要工作。
2. **证据优先**：涉及代码现状、运行行为或外部接口的判断，应优先使用源码、现有测试、实际命令或最小验证实验。纯逻辑矛盾可以使用准确引用和具体反例证明。
3. **一次处理同类问题**：评审问题必须说明根因和检查范围，并列出该范围内全部同类问题。裁决或修复时应再次检查同类位置并一次处理完毕。
4. **设计不追求完美**：设计阶段只消除会使实施方向失效、目标受损或里程碑不可执行的问题。验证程序仍可加强、局部表述可改善等事项不得单独延长设计循环。
5. **验证采用项目原有体系**：优先使用项目已有测试、合同、运行脚本和真实环境。只有任务确有需要时才增加专用验证程序。
6. **协议版本固定**：本次运行始终使用本文件中的规则，不得在运行中同步其它版本。
7. **会话自主性**：设计、评审、实现和审计分别在独立会话中完成。各会话不得向用户询问如何继续；遇到未明确规定的事项，应依据任务目标、项目原则和已取得的证据作出合理决定，并记录理由。

### 文件和状态

本次运行只要求以下流程文件：

- 设计文档：`{{DOC_DIR}}/{{SLUG}}.md`
- 设计评审：`{{DOC_DIR}}/{{SLUG}}-review.md`
- 实现审计：`{{DOC_DIR}}/{{SLUG}}-audit.md`
- 运行记录：`{{DOC_DIR}}/retro.md`

设计评审和实现审计文件每轮覆盖写入，只保留当前结论。`retro.md` 每轮追加一行简要记录，并在任务终止时补充总结。

设计文档开头必须维护：

```text
status: 设计中 | 实现中 | 已完成 | 不可实现 | 协议失败
design-round: d/15
implementation-round: k/N
current-milestone: M-xx
current-milestone-reopens: r
convergence-mode: normal | domain-review | milestone-review
next-action: <下一实现轮首先完成的具体工作；没有时写“无”>
```

计数规则：

- `d` 由设计裁决轮增加，设计评审轮不增加。
- `k` 由实现轮增加，审计轮不增加。
- `r` 是当前里程碑因实现缺陷从 `待审`退回`开放`的累计次数；验证缺口直接加强后产品仍正确、或里程碑本来就是`开放`时不增加。
- 设计完成时，以初始里程碑数量 `M` 计算 `N = 5 × M`。这是所有里程碑共享的总预算，不设单个里程碑预算。
- 实现中可以调整未完成里程碑，但 `N` 不随拆分或合并而改变。

里程碑状态只有：

- `开放`：尚未完成。
- `待审`：实现轮已取得通过证据，等待独立审计。
- `已完成`：审计轮独立复验通过。

实现轮不得将里程碑标记为 `已完成`。

#### Reopen、缺陷复盘与收敛

设计文档中每个里程碑还必须维护 `reopen-count` 与 `defect-mechanisms`：

- `reopen-count`：审计确认实现缺陷并把该里程碑从`待审`退回`开放`的次数。纯验证缺口、原本就是`开放`的里程碑不计。
- `defect-mechanisms`：以「根因机制·模块」为键的计数。审计轮每确认一个范围内的实现缺陷（「缺陷复盘」第 8 条），就为它的键加 1（同一审计轮同一个键只加一次），不论里程碑原本是`待审`还是`开放`。机制只能取「缺陷复盘」中的机制词表；模块写项目的规范模块根。可以附简短说明，说明不参与计数，也不得通过改写说明或改换模块写法规避升级。

旧任务首次采用本机制且缺少计数时，下一审计轮根据 `retro.md` 中该里程碑真实的审计记录初始化。

触发规则：

- 某个「机制·模块」计数达到 2：`convergence-mode: domain-review`，对该机制执行完整复盘。
- 同一里程碑 `reopen-count` 达到 3：`convergence-mode: milestone-review`，对该里程碑出现过的每个机制执行完整复盘。
- `milestone-review` 优先级更高；收敛模式一旦触发，直到里程碑关闭前不得恢复为 `normal`。之后又有机制计数达到 2 时，同样对它执行完整复盘。

触发收敛模式的审计轮必须在当前实现审计文件顶部维护 `## Convergence Note`，不得新增流程文件。Note 只记录尚未闭合的差异，不复制 Task、设计正文或完整历史，并固定为四部分：

1. **Remaining closure map**：未闭合的「机制·模块」、对应缺陷卡片的摘要及当前失败证据。
2. **Root cause and scope**：完整复盘的结果：逃逸证明、逃逸类别、来自权威来源的同类普查，以及前轮为何漏检。
3. **Next implementation batch**：按依赖顺序写出下一轮必须达成的结果：要成立的不变量与结构性质、输入范围与判定标准、完成条件。只写要达成什么，不写实现方案（见「缺陷复盘」第 5 条）。只列范围内且未分配的完成条件；范围外与已分配的缺陷只列登记位置或去向（见「缺陷复盘」第 8 条）。
4. **Closure gates**：当前应红、完成应绿以及不得退化的命令，包括结构性质的机检命令与缺陷注入方法。缺口类门禁使用「缺陷复盘」第 3 条 B 类补救从权威来源（类型、注册表、状态机、生成物、可执行普查，或对尚无实例的形式而言定义该形式的文法或规范）得到的全集，不得以手写列举或审计发现缺口时使用的探针代替。普通模式下，`next-action` 中的完成条件同样适用本款。

后续审计覆盖写审计文件时必须保留并更新该 Note，直到里程碑关闭。`next-action` 应简短指向 Note 的下一实施批次；`retro.md` 记录 reopen 次数、各「机制·模块」计数、收敛模式、完成的结构性修改及关闭轮次。

#### 缺陷复盘

审计确认的每个实现缺陷都按以下方法复盘。项目画像给出「缺陷复盘协议」（机制词表、逃逸类别细分、逃逸证明工具、主干既有缺陷的登记流程）时，使用项目画像中的词表与工具；没有给出时使用本节的默认词表和方法。

1. **缺陷卡片**：每个实现缺陷在审计文件中写明现象、证据、根因机制与模块、在任务基线 revision 上能否复现、逃逸证明、逃逸类别、同类普查和补救。
2. **逃逸证明**：在缺陷修复前的代码上运行实现轮声称通过的验收命令，以及离缺陷最近的既有测试，记录结果属于哪一种：未执行、执行但看不到失败、失败但被忽略、不存在相关测试。
3. **逃逸类别与补救**：
   - **A 验证体系缺陷**：相关验证没有执行、被跳过、判定条件看不到失败，或替身、夹具与真实实现不一致。补救是修复验证机制本身（接线、取消跳过、修正判定条件并加正向对照、替换失真的替身），不只是增加一个用例。
   - **B 用例不足**：验证机制正常，但缺少维度或实例。补救是从权威来源（注册表、生成物、状态机、类型定义或可执行的普查）列出全部同类实例，并扩展模型、参考函数或输入生成器；只有确实没有可用模型时才补充单个用例，并写明理由。
   - **C 其他**：设计没有定义该行为、缺陷位于第三方或框架等。写明需要的设计裁决或上游修复。
4. **完整复盘与结构性修改**：某个机制触发收敛时，对它的全部缺陷执行逃逸证明与同类普查，并要求下一实施批次做出使该机制在结构上不能再发生的修改，例如一个事实只有一个写者或读者、从权威来源派生、类型化的载体、统一的参考函数。对同一事实存在多个副本、多个写者，或多处各自推导同一事实的机制（如多副本漂移），结构性修改必须使该事实只剩一个写者和一个推导位置：删除其余副本、写者或推导，或把它们改为调用同一个从权威来源计算的函数。比较、校验或普查副本之间是否一致的检查属于验证补救（A 或 B 类），不算结构性修改；保留副本而增加检查的，不满足本条。结构由实现轮设计，并同步修订设计文档中对应的方案。审计按三项验收：结构性质可以机检（类型、模块边界，或列举全部写者与读者的契约测试；多副本类机制须由可执行的普查列举该事实的全部写者与推导位置，且各恰好一个）；人为加回第二条路径（第二个写者或读者、手写副本、未类型化的字段）时测试变红；逃逸类别要求的验证补救已经完成。结构完成之前，同一机制的新实例照常认定为实现缺陷。
5. **审计只写要达成什么**：审计可以用候选修改验证可行性，但候选修改不属于实施批次；实现轮自行设计实现，与审计的可行性验证不同时说明理由。
6. **主干既有缺陷**：在任务基线 revision 上能复现的缺陷不是本任务引入的。先按第 8 条判定作用范围：范围内的在本任务中修复，范围外的按第 8 条处理；两者都按项目画像的缺陷复盘协议登记，画像没有规定时在 `retro.md` 中单独列出。本任务引入的缺陷只记录在审计文件中。
7. **超出任务范围的修改**：结构性修改需要 Task 明确排除的改动（例如 Task 规定不改的协议或框架）时，按 C 类写明需要的裁决或上游修复，并按项目的 issue 规则建立后续任务。该缺陷若违反 Task 要求或里程碑验收，里程碑仍不能关闭。
8. **作用范围**：审计对每个缺陷（包括记为备注但已复现、或有明确代码证据的偏离），以及里程碑验收报告的每个失败，判定它是否在当前里程碑的作用范围内，并在缺陷卡片中写明依据。
   - **对象**：缺陷所在的内容（代码、数据、文档或配置中出错的那部分）。以缺陷被发现时为准：修一处即可消除全部位置的，是同一根因，任一位置在范围内即整体在范围内；需要分别修改的多个位置，是同一机制的多个实例，逐个判定。
   - **范围内**，满足下列任一款：
     - (a) 缺陷使当前里程碑某条覆盖要求或结果所陈述的行为、取值或结构性质（例如「全部查表」「只有一个写者」）不成立；或者缺陷所在内容包含于这些要求或结果要求创建、修改或修复的对象之中（例如要求修改一条记录，则记录中的任一句）。只要求阅读、确认或报告的对象不因此进入范围，对其正确性的要求按行为判据判定。要求以文件路径指明对象的位置时，对象是该位置上被要求处理的部分，不是整个文件。结果要求创建的交付物（例如一个 PR）只纳入其中为实现该结果的内容。为说明依据、约束或排除而提及的对象不算；验收命令不扩大本款的对象。以类定义的对象（例如「同类写法」「每条红灯」）指从权威来源枚举出的成员，卡片写明枚举来源；无法枚举时按本款的行为判据判定。
     - (b) 缺陷由本任务的改动造成，在任务基线上不能复现（任一里程碑、任一轮次）。
     - (c) 在缺陷被发现之前，本任务为实现当前里程碑的结果而新建或修改了缺陷所在的内容，包括为范围内对象编写的测试、检查器与证据。
   - **范围外**：不满足上述任何一款。为修复、登记或检查范围外缺陷而做的新建或修改（包括登记条目、证据，以及检查范围外对象的检查器）不使对象进入范围，这些内容上的缺陷与失败同样在范围外，不需要基线运行；其中由本任务造成的记在审计文件中，由项目画像的登记流程修正。本任务新建的检查器漏检时，按它漏检的对象判定；尚无实际漏检实例的形式缺口按下一款判定。
   - **同时服务范围内与范围外对象的内容**（例如检查器的人口同时包含两类对象，或一条登记条目同时登记两类缺陷）：按出错部分已经造成误判、漏判或误述的对象判定：涉及范围内对象的在范围内，其余在范围外；同一处错误同时涉及两类对象时按范围内。尚无实际漏检实例的形式缺口，只有范围内对象的现有内容含该形式时才在范围内。
   - **优先级**：(a) 优先于范围外一款的排除句；排除句优先于 (b)、(c)。
   - **归属与分配**：
     - 一个对象在多个里程碑的范围内时，结果有区分的，按缺陷违背的那句结果所属的里程碑；没有区分的，归其中尚未完成、编号最小的里程碑。已完成的里程碑不重新打开；归属于已完成里程碑的缺陷，归当前里程碑。
     - 范围内的缺陷可以分配给后续里程碑或独立 issue，条件是二者之一：该缺陷存在时，后续里程碑的结果陈述不能成立（只要求登记记录的句子，例如「记录写成 closed」，不算）；或经负责人确认的变更作出该分配。实现轮按模板修订未完成里程碑的结果后，以修订后的结果判定。审计写入设计文档的备注本身不是分配依据。原因未定位的失败同样适用本款。审计在卡片中写明分配及其依据；未分配的范围内缺陷是当前里程碑的完成条件。
   - **范围外缺陷的处理**：审计逐条写出核对过的要求编号与结果句子，以及不相符的理由；按项目画像的缺陷复盘协议登记（缺陷条目、仍失败检查的 owner 与期限、后续 issue）。它不成为本里程碑的完成条件，不计入 `reopen-count` 与 `defect-mechanisms`。登记不等于机制闭合：同一机制在范围内再出现时照常计数。
   - **验收中的失败**：里程碑验收报告的失败（包括结构性质的检查、整条测试 lane、全量测试、远端 CI 与退出码类判据）同样按本条判定。
     - 原因已定位到内容的失败按缺陷判定；竞态定位后按参与竞态的代码判定。以下各款只用于原因尚未定位的失败，其对象是失败的检查所检查的对象。
     - 基线是不含本任务任何改动的检出（优先当前主干，无法运行时用任务基线 revision），在同一机器与同一配置上实际执行同一检查；本任务新建的检查叠加到基线检出上执行。合入了本任务提交的分支、代码阅读与 `git blame` 都不是基线运行。
     - 失败所在对象不在范围内时，审计取得基线运行结果。基线上的执行次数（同一检查在同一条件下的执行次数）不少于分支上；同样出现（包括间歇出现）的，为范围外，按上一款登记，不阻断本里程碑，也不因「不得新增失败」或整体退出码成为完成条件。在取得基线结果之前，或基线上不出现的，该失败在范围内。
     - 环境失败指机器状态或外部服务造成、与本仓库代码无关的失败，须有证据：同一修订在环境恢复后通过，或错误直接指向机器状态或外部服务。只在负载或特定交错下出现的竞态是代码缺陷，按对象判定。单独重跑通过既不是基线运行，也不是环境证据。环境失败不是缺陷；在取得环境正常的运行结果之前，对应验收视为未执行。
     - 范围内的失败阻断验收，未分配时一直是完成条件；里程碑因此不能完成时置为`开放`，但不计入 `reopen-count`，定位为实现缺陷后才计入 `reopen-count` 与 `defect-mechanisms`。
     - Task 要求对失败的处理另有规定时，以 Task 要求为准。
   - **无法判定时**：按本条仍无法判定的，按范围内处理，卡片写明无法判定的原因。
   - 除 (b) 款与失败的基线归因外，判定不看缺陷能否在任务基线上复现，也不看它与范围内缺陷是否属于同一机制。
   - 范围内且未分配的缺陷是当前里程碑的完成条件：不论能否在任务基线上复现，都在本任务中修复，计入 `defect-mechanisms`，里程碑为`待审`时计入 `reopen-count`，并按本节触发收敛与结构性修改。
   - 卡片的依据栏：(a) 写要求编号或结果句子，以及不成立的行为或包含它的对象；(b) 写引入它的提交或轮次；(c) 写新建或修改该内容的提交或轮次；分配写去向与依据；范围外写核对过的要求与结果及理由。

默认机制词表：

| 机制 | 含义 |
|---|---|
| 多副本漂移 | 同一事实或规则在两处以上实现或读取，副本之间出现差异 |
| 手工注册表遗漏 | 手工维护的列表、映射、分支或白名单漏项 |
| 跨边界丢字段 | 值在跨越边界（接口、序列化、进程、存储映射、工具输入输出）时丢失或被错误转换 |
| 状态模型缺维度 | 状态模型缺少状态或维度，或把两个状态混为一个 |
| 异步竞态 | 顺序或交错问题：竞态、更新丢失、过期闭包、乱序事件 |
| 生命周期未闭合 | 资源、订阅、租约、计时器或操作没有释放，或没有到达终态 |
| 失败通道丢失 | 错误被吞掉、没有传播、没有呈现，或被错误分类 |
| 性能放大 | 工作量被放大：每次变更全量重建、平方级循环、无界增长 |
| 上游契约不符 | 对外部服务或依赖契约的假设与实际不符 |
| 配置接线 | 配置、环境、构建常量、依赖或进程入口接线错误 |
| 第三方缺陷 | 缺陷位于第三方或框架包内 |
| 其它 | 以上都不是；必须写明理由，下一审计轮可以重新归类 |

### 设计文档要求

设计文档应包含：

1. **背景和现状**：只写与任务有关的事实，并给出代码、文档或运行证据。
2. **目标与非目标**：逐项对应 Task 的编号要求。
3. **方案**：只保留一个明确方案，说明关键决策及理由。
4. **里程碑**：按依赖顺序编号为 `M-01..M-N`。
5. **风险与验证安排**：区分设计期必须验证的风险和可以在实现期验证的风险。
6. **基线**：记录任务开始时的 Git revision、工作树状态，以及与本任务相关的已有测试结果。

每个里程碑必须包含：

- 可独立观察的结果。
- 覆盖的 Task 要求编号。
- 前置里程碑。
- `reopen-count` 与 `defect-mechanisms`，初始分别为 `0` 与空集合。
- 验收命令；如果命令尚不存在，应准确说明实现阶段需要新增的测试或运行入口。
- 最新证据。

里程碑应当是可以运行和验证的阶段性系统状态。第一个里程碑应尽早消除最大的技术不确定性；对于跨组件任务，通常应建立最小端到端链路。

设计阶段采用精简的可执行验收：

- 每个里程碑至少有一个可执行验收入口或明确的待建测试。
- 并发、崩溃、切换、删除、权限和不可逆数据变更等高风险行为，至少提供一个能区分错误实现的负向对照或最小验证实验。
- 不要求为每个断言建立专用 schema、夹具集合或通用断言框架。

### 设计复审条件

只有以下六类问题可以要求下一轮设计评审：

1. **关键事实错误**：方案依赖的技术、接口、代码行为或运行条件与实际不符，可能使方案整体失效。
2. **内部逻辑矛盾**：两项要求不能同时满足、关键路径不可达，或里程碑按设计无法通过验收。
3. **违反项目原则**：方案违反项目权威规则中的架构职责、数据原则或工程约束。
4. **违反任务目标**：方案偏离 Task 的目标、范围或硬性约束。
5. **里程碑不可执行**：里程碑过大、依赖顺序错误、验收不明确，或明显不能在合理实现轮次内完成。
6. **必须提前验证的重大风险**：该风险无法在实现环境中及时验证，若推迟会使后续实现整体失效。

验证还可以更严格、测试还可以增加、资料性说明可以改进、局部命名可以优化等问题，均不得单独触发下一轮设计评审。

若同一设计领域第二次出现需要复审的问题，裁决轮不得继续逐句补充说明。应根据问题性质，将完整行为整理为状态表、真值表、参考函数、结构化清单或最小契约测试，并一次检查全部输入情况。

### 运行记录

任务终止时，`retro.md` 只记录可核对事实：

- 终止状态和原因。
- 设计轮数、实现轮数及各里程碑最终状态。
- 设计阶段采纳的问题类别。
- 审计发现的实现缺陷数与验证缺口数，以及实现缺陷的逃逸类别分布。
- 各里程碑 reopen 次数、各「机制·模块」计数、收敛模式、完成的结构性修改及关闭轮次。
- 主干既有缺陷及其登记情况。
- 自动调整里程碑的次数和原因。
- 是否发生人工介入；按本文件正常运行时应为 0。
- 预算是否满足，以及未完成任务的明确阻塞。
- 对协议的改进建议，最多三项，并说明对应证据。
