### 共同原则

1. **产品结果优先**：下列规范用于促进任务完成，不得为了完善流程文件而延迟主要工作。记录写结论、证据位置与下一步；git 已记录改动，不为证明没有改动什么而逐文件计算哈希、封存清单或复述未变化的状态与计数。
2. **证据优先**：涉及代码现状、运行行为或外部接口的判断，优先使用源码、现有测试、实际命令或最小验证实验。纯逻辑矛盾可以用准确引用加具体反例证明。
3. **主张按性质取证**：每种主张用最便宜的充分证据确立，不得要求更强的一种。**决定**（方案、事实归属、顺序、接口、取舍）靠论证加同一轮的最小验证实验。**全称性质**（全部、每个、任一）靠验收契约中的判定器在真实人口上运行确立：立项期只要求定义、一次真实切片上的运行计数与单位成本，失败与未知归零是实现期的工作。**语义性质**（只能靠判断的类别，例如注释与文档中的陈述）靠 Task「价值判断」中声明的固定人口、抽样策略与吞吐估算。固定的是应覆盖对象的定义与权威来源，不是某次枚举的行号或输出快照；成员移动、替换或退出须保留来源与行为证据并经独立复核，既不因旧坐标失效永久增加未知，也不因当前漏枚举就撤销覆盖。判定器由三部分定义：人口从结构性权威派生（类型、符号引用、注册表、生成物、文件全集、语法树节点种类全集），在契约中命名，不得以本任务改动的文件为人口；「本任务改动或要求处理的对象的全部内容，按文件、模块或记录整体计」只作语义性质的成员集合；归类带未知分支，不能识别或需要判断而未判断的成员判「未知」并失败；信任基写明接受而不证明的前提，只允许平台有文档的语义和仓库中已在运行的门禁。手写清单、选定模式检索与选定探针都不是判定器。某个成员未列出是实现细节；定义缺少三部分之一是契约缺陷，修正是补全定义并重跑人口，不是补列词表、句型、模式、扫描轴或站点。
4. **返工检验决定立项期义务**：某个主张若在实现期被证伪，会导致重做已完成里程碑的工作、改变方案或跨里程碑接口、执行或撤销不可逆操作、或突破用户明确的硬约束，它才必须在立项期关闭；其余由所在里程碑的验收发现。立项期答不了的量不阻塞立项，写成风险清单的一条：该量、依赖它的决定、每种结果下预先决定的分支，并排进最早的里程碑用造的方式消除。
5. **目标不变，方案按证据修正**：核心目标要求的结果与质量标准（错误定义、应覆盖对象、残余容忍）、用户明确的范围、权限与资源约束，以及项目权威规则不得放宽。判定器形式、人口派生方法、审阅流程、证据载体、附加完成条件、决定、风险、进度量与圈计划是可复评的执行依据；其中本身就是用户或项目明确要求的交付结果或约束的，仍按该要求处理，不因名称或写入 Task 的位置决定其性质。修正由独立评审按「复评与停止」核验并更新；日常契约定义缺陷由验收确认、工作轮修复并重跑人口，未受影响的成员结论保留。改变进度量定义或单位时先存快照，保留旧口径与完整序列，从实测新值开始，不把改口径记为完成了工作。修正不得通过删去应覆盖的对象、放宽残余、扩大信任基或隐藏失败来获得通过；信任基只能在 Task 允许的范围内收窄。
6. **同类一次处理**：评审与验收的问题写明根因与检查范围，范围内全部同类由判定器列出并一次处理。同一机制在同一里程碑内复现时，按「缺陷复盘」第 4 条判断是否需要结构性修改。同类只在作用范围内认定（「缺陷复盘」第 8 条），不得以同类为由把范围外对象纳入本任务。
7. **竖切增量**：每个里程碑是可运行、可验收的系统状态。第一个里程碑消除风险清单上最高的一条（清单为空时只要求竖切），并在一个真实切片（一个变体、一个槽位、一个入口）上端到端跑通，端到端指产品路径在该切片上真实运行且核心目标契约在该切片上给出通过与失败的计数；先竖切，再扩人口。横向先建完一层再接下一层的计划不接受。
8. **判断归负责的角色**：各会话使用本文件，不自行同步其它版本；用户明确要求迁移时，保存旧任务、状态与证据，记录修订范围，从指定恢复点继续。立项、评审、工作轮、验收轮在独立会话中完成；遇到未规定事项依据任务目标、项目原则与证据决定并记录理由，不要求用户选择下一步。进度量、圈数与估算是判断的输入，不是判断本身：是否继续、何时复评、某个缺陷是否阻塞，由负责的角色依据证据判断并写明理由；作出继续或接受下一步的判断时，写下下一圈结束时可以核对的预期与预计投入，下一个独立角色先核对它。编号要求中的结果、质量与明确约束遵循共同原则 5；方法与附加要求可由评审依据证据取舍并写入设计，不要求先证明原文不可达。影响整体方案、验收方法或工作组织的取舍交独立复评；估算不足先复评，不以旧估算为理由删减要求。

### 资源等待不结束轮次

本节适用于所有阶段，先于计数、结束和启动下一 session 的步骤执行，最后一圈也不例外。执行资源只指测试与运行资源及其排队入口；上游依赖未发布、权限未批不是资源等待，是风险清单的条目，按其分支处理。本轮必需验证（本轮按工作轮或验收轮规定要运行的验收命令与契约运行）因执行资源暂不可用而未运行或中断时，必须在当前 session 内使用等待工具等待，资源可用后继续执行；不得因等待结束 session、增加 `d` 或 `c`、启动下一 session，或判定任务失败。

优先使用项目已有的排队机制，遵守资源准入规则。等待工具单次返回或排队命令超时不代表等待结束：检查原进程，仍在排队或运行则继续等待，已因排队超时退出则在同一 session 重新排队，避免重复启动。没有排队入口时，用等待工具分段等待并复查准入条件。资源恢复后复核代码与环境，补跑缺失或已失效的验证；实际执行后发现的失败按原缺陷协议处理。本任务自己的运行环境（例如本工作区的栈）停止时，按项目规则恢复它是本轮工作，不是等待。

用户明确停止或宿主强制中断时，在已有 `retro.md` 保存当前轮、已完成工作、等待资源、进程与待执行命令，不自动交接；恢复后核对状态并继续同一轮。等待仍受用户明确的硬预算约束，耗尽时按「停止尝试」结束；不得自设等待时限作为中断理由。已证实的其它技术或权限问题按复评与终止规则处理。

### 文件与状态

本次运行只要求以下流程文件：

- 设计文档：`{{DOC_DIR}}/{{SLUG}}.md`
- 评审账本：`{{DOC_DIR}}/{{SLUG}}-review.md`，跨轮追加，不覆盖。
- 验收记录：`{{DOC_DIR}}/{{SLUG}}-acceptance.md`，每圈覆盖，保留四个常设段落（见验收轮）。
- 运行记录：`{{DOC_DIR}}/retro.md`，每轮追加一条，内容见「运行记录」。
- 证据目录：`{{DOC_DIR}}/evidence/`。runner 写的设计快照在 `evidence/snapshots/design-d<d>/`（再入为 `design-r<n>/`），立项与各轮的实验输出放在 `evidence/d<d>/`，每圈的运行输出在 `evidence/cycle-<c>/`；不要把实验输出放进 `snapshots/`。
- 可执行参考：`{{DOC_DIR}}/reference/`。

设计文档开头维护状态头，字段与取值固定：

```text
status: 立项中 | 实现中 | 已完成 | 停止尝试 | 不可实现 | 协议失败
design-round: d/3
cycle: c/C
current-milestone: M-xx
milestones: <已完成数>/<总数>
risks: <已退休数>/<总数>
progress: <进度量名>(<down|up>): v0, v1, ...
reentries: n
next-step: <验收轮或评审接受的下一步；立项通过时由评审轮写 M-01 的第一步>
```

账目由 `{{RUNNER}}` 维护，各任务只调用它，不手改数字。runner 只记录事实，不判断进展，也不触发任何动作：

```bash
node {{RUNNER}} {{DOC_DIR}} state set <key> <value>      # 改一个状态头字段
node {{RUNNER}} {{DOC_DIR}} snapshot design-d<d>         # 改写设计前存快照
node {{RUNNER}} {{DOC_DIR}} diff design-d<d-1>           # 上一快照与当前设计的差异
node {{RUNNER}} {{DOC_DIR}} ledger add <id> <类别> <攻击对象> <后果或内容>
node {{RUNNER}} {{DOC_DIR}} ledger set <id> <open|closed|rebutted|note> [说明]
node {{RUNNER}} {{DOC_DIR}} progress append <value>      # 记录本圈实测值
node {{RUNNER}} {{DOC_DIR}} progress redefine "<量名>(<down|up>)" <value>  # 换量：里程碑切换、口径修正或判定器建成；旧序列保留在 || 之前
node {{RUNNER}} {{DOC_DIR}} cycle advance                # c 加一
```

脚本不可用时，手工完成同样的更新并在 `retro.md` 记一行原因。

计数与状态：

- `d` 由评审轮在结论为「需要修订」时增加；立项与再设计不增加。
- `c` 由验收轮在一圈结束时增加；运行期每次复评作出结论也计一圈，再设计不另加。
- `C` 是当前的预计总圈数：立项按「设计文档要求」第 7 项给出，独立评审依据实测修正为已用圈数加剩余工作估算，保留旧值与理由。它是判断进展的参照，不是用户的硬预算；到达它本身不触发任何动作。
- `progress` 记录进度量的实测序列。进度量是观测工具，须能反映当前里程碑剩余的完成条件；量已到终点仍有范围内工作、新增的完成条件不在量内、口径失真，或量不动而工作确有推进时，由验收或评审换量，旧序列保留。量的涨落是判断的证据，不自动决定继续、复评或停止。
- `next-step` 是下一圈工作的唯一权威；验收记录的「下一步要达成的结果」是它的展开，两者不一致时以 `next-step` 为准。

里程碑状态只有：`开放`（尚未完成）、`待审`（工作轮已取得通过证据，等待验收）、`已完成`（验收轮独立复验通过）。工作轮不得把里程碑标记为 `已完成`。

#### 缺陷复盘

验收确认的每个实现缺陷都按以下方法复盘。项目画像给出「缺陷复盘协议」（机制词表、逃逸类别细分、逃逸证明工具、主干既有缺陷的登记流程）时，使用项目画像中的词表与工具；没有给出时使用本节的默认词表和方法。每张缺陷卡片写明根因机制（取词表）与模块（项目的规范模块根；同一事实的多个副本分布在多个模块时写「跨模块」）；验收记录与证据目录保留当前里程碑的全部卡片，供判断复现。

1. **缺陷卡片**：每个实现缺陷在验收记录中写明现象、证据、根因机制与模块、在任务基线 revision 上能否复现、逃逸证明、逃逸类别、同类普查、补救，以及第 8 条的阻塞判断与依据。
2. **逃逸证明**：在缺陷修复前的代码上运行工作轮声称通过的验收命令，以及离缺陷最近的既有测试，记录结果属于哪一种：未执行、执行但看不到失败、失败但被忽略、不存在相关测试。
3. **逃逸类别与补救**：
   - **A 验证体系缺陷**：相关验证没有执行、被跳过、判定条件看不到失败，替身、夹具与真实实现不一致，或判定器定义缺少三部分之一而在信任基内静默放过。补救是修复验证机制本身（接线、取消跳过、修正判定条件并加正向对照、替换失真的替身、补全判定器定义并重跑人口），不只是增加一个用例。
   - **B 用例不足**：验证机制正常，但缺少维度或实例。补救是按共同原则 3 以判定器列出全部同类实例，并扩展模型、参考函数或输入生成器；只有确实没有可用模型时才补充单个用例，并写明理由。
   - **C 其他**：设计没有定义该行为、缺陷位于第三方或框架等。写明需要的设计再入或上游修复。
4. **复现与结构性修改**：同一里程碑内同一「机制·模块」再次出现时，对它的全部卡片执行逃逸证明与同类普查，并判断复现的原因。原因在结构上（同一事实有多个副本、多个写者或多处各自推导；缺少权威来源、类型化载体或统一的参考函数）时，下一圈做出使该机制在结构上不能再发生的修改，它是当前里程碑的完成条件；判断原因不在结构上时，在卡片写明理由，由下一圈验收或评审复核。多副本、多写者或多处推导的结构性修改必须使该事实只剩一个写者和一个推导位置；比较、校验或普查副本之间是否一致的检查属于验证补救，不算结构性修改。结构由工作轮设计，并同步修订设计文档中对应的决定。验收结构性修改时：结构性质由判定器机检（类型、模块边界，或从权威来源列举全部写者与读者的契约测试），只识别已列出形式的检查不算；至少用一个从人口权威派生、不在工作轮目录内的变体核验，人为加回第二条路径或以未曾列出的写法加回时测试变红；逃逸类别要求的验证补救已经完成。结构完成之前，同一机制的新实例照常认定为实现缺陷。只能靠语义判断的类别没有可机检的结构性质：结构性修改是在成员集合中删去副本或改为引用权威；载体是记录或流程时，结构性修改是判定器新增一条有红对照的机检规则；验收按 Task 声明的抽样策略终止。
5. **验收只写要达成什么**：验收可以用候选修改验证可行性，但候选修改不属于下一步，不进入 `evidence/`，验收记录只写可行性结论；工作轮自行设计实现，与验收的可行性验证不同时说明理由。
6. **主干既有缺陷**：在任务基线 revision 上能复现的缺陷不是本任务引入的。先按第 8 条判断是否阻塞：阻塞的在本任务中修复，不阻塞的按第 8 条登记；两者都按项目画像的缺陷复盘协议登记，画像没有规定时在 `retro.md` 中单独列出。本任务引入的缺陷只记录在验收记录中。
7. **超出任务范围的修改**：结构性修改需要 Task 明确排除的改动时，按 C 类写明需要的再入或上游修复，并按项目的 issue 规则建立后续任务。该缺陷若违反 Task 要求或里程碑验收，里程碑仍不能关闭。
8. **作用范围与阻塞**：验收对每个缺陷，以及里程碑验收报告中每个失败，判断它是否阻塞当前里程碑，在卡片中写明依据；下一圈验收与评审可复核并改判。
   - **阻塞（范围内）**，满足任一项：缺陷使核心目标、Task 编号要求（按设计中经取舍的口径）或当前里程碑某条结果所陈述的行为、取值或结构性质不成立，或缺陷所在内容正是这些要求或结果要求创建、修改或修复的对象；缺陷由本任务的改动造成，在任务基线上不能复现；缺陷位于本任务为实现当前里程碑而新建或修改的产品内容中。只要求阅读、确认或报告的对象、为说明依据或约束而提及的对象，以及验收命令本身，都不因此进入范围。辅助本任务验证的测试、检查器、可执行参考与证据出错是验证缺口（见验收轮第 3 步），不是产品缺陷；这些内容本身是 Task 要求交付的产品能力或对象时，其违反要求的错误仍是实现缺陷。
   - **不阻塞（范围外）**：不满足上一项。逐条写出核对过的要求或结果句子与不相符的理由，按项目画像的缺陷复盘协议登记（缺陷条目、仍失败检查的 owner 与期限、后续 issue），不成为完成条件。为修复、登记或检查范围外缺陷而做的改动不使对象进入范围。登记不等于机制闭合：同一机制在范围内再出现时照常认定。
   - **分配**：阻塞的缺陷默认是当前里程碑的完成条件；可以分配给后续里程碑或独立 issue，条件是该里程碑的结果依赖它修复，或评审确认新的分配。已完成的里程碑不重新打开，归属于它的缺陷归当前里程碑。
   - **原因未定位的失败**：在不含本任务任何改动的基线检出（优先当前主干；本任务批次已合入主干或主干无法运行时用任务基线 revision）上，以同一机器与同一配置实际执行同一检查；本任务新建的检查叠加到基线上执行。基线上出现（含间歇出现）一次即判为不阻塞，按上一项登记；基线执行次数达到分支上的次数仍不出现，或尚未取得基线结果时，按阻塞处理。合入了本任务提交的分支、代码阅读与 `git blame` 都不是基线运行。环境失败须有证据：同一完整命令在采样证明空闲的机器上通过（focused 重跑不算），或错误直接指向机器状态或外部服务；只在负载或特定交错下出现的竞态是代码缺陷；单独重跑通过既不是基线运行也不是环境证据；取得环境正常的运行结果之前，对应验收视为未执行。Task 对失败处理另有规定时以 Task 为准。
   - **无法判断时**按阻塞处理，卡片写明无法判断的原因。

### 设计文档要求

设计文档是立项的产物，包含七部分，每部分只陈述当前结论，每个决定、事实或规则只在一处陈述，其它位置引用该处；过程写入 `retro.md`，实验输出放在 `evidence/`。再设计时改写对应段落，不在原文之后追加补充说明；被替代的内容留在快照中，正文不保留历史。设计文档保持一次能读完的篇幅。

1. **背景与基线**：只写与任务有关的事实并给出代码、文档或运行证据；记录任务开始时的 Git revision、工作树状态与相关的已有测试结果。
2. **目标与完成定义**：逐项对应 Task 的核心目标与编号要求。每条核心目标指明它的验收契约（第 5 项）；涉及全体对象的编号要求写明确立方式，二选一：判定器（引用契约）或语义性质（引用 Task「价值判断」中的固定人口与抽样策略）。经评审或验收取舍的要求在该要求下写取舍后的口径、理由与证据位置。完成定义是：全部核心目标的契约通过，全部风险退休，全部里程碑 `已完成`。
3. **决定登记**：只保留一个明确方案，拆成编号决定 `D-01..D-n`。每条写结论、理由、证据位置、被否的替代方案，以及若它错了的返工后果（重做哪个里程碑、改哪个接口、哪个不可逆操作）。被驳回过的异议在该决定下记一行结论，再次提出须有新证据。
4. **风险清单**：编号 `R-01..R-n`，每条写不确定的量、依赖它的决定和消除方式：本轮用真实代码路径的最小实验退休，或放进最早合适的里程碑，写明如何取得证据、结果会怎样改变后续工作。按返工检验属于立项期义务的风险须在立项期退休。新证据暴露的风险由独立评审核验后更新，不为未知结果穷举未经验证的分支。
5. **验收契约**：每条核心目标一份。字段固定：人口的权威来源；信任基（接受而不证明的前提）；未知即失败；残余容忍（从 Task「价值判断」抄录，不得自定）；资格化方式（只在核心目标本身陈述判别力，例如「删去任一接线合同变红」时，变异算子集从权威来源派生并全量统计检出比例，自选注入不能代替；其它契约写一次正向对照与一次负向对照）；一次真实切片上的运行：通过、失败、未知的计数，失败与未知清单位置，单位成本（由实际处理不少于 5 个成员的样本测得并取中位，人口不足 5 时全查，不得估计），该切片在立项会话内实际处理的成员数（处理指使成员得到最终结论：修复后通过，或作出记录的裁定；判定器扫过不算处理）。切片须在交付工作区的真实树上运行（不在实验树上），须含通过与失败或未知各至少一个成员，写明占人口的比例，进度量初值取该运行的计数；切片处理成员数乘单位成本应与立项会话处理该切片的实际耗时大致相符。Task 准入分类为 A 类时，契约是既有测试、旅程与门禁的命令清单及其预期结果；为 C 类时，契约写固定人口、抽样策略、吞吐估算与裁定记录的位置，真实切片运行指对不少于抽样样本量的成员作出记录的裁定；C 类契约通过的定义是：全部成员有记录的裁定结论，且按 Task「价值判断」声明的抽样策略与通过标准（样本量、种子、错误的定义、允许的残余）复核一次全样本后满足该标准；模板不自定零错误。
6. **圈计划**：里程碑 `M-01..M-N` 按依赖顺序编号。每个写可观察的结果、覆盖的 Task 要求、前置里程碑、验收命令（尚不存在时说明需要新增的测试或入口）、退休的风险、进度量、估算圈数及依据和最新证据。第一个里程碑须是竖切片并退休最高风险。进度量的初始选择：A 类为已完成里程碑数或 Task 定义的累计有效绿样本数（up）；B 类为契约失败加未知数（down）；C 类为有效已裁定成员数（up），开放缺口不计。判定器未建成时可用验收失败数，建成后以首次计数换量。一个量反映不了的完成条件（例如结构性修改）在里程碑下逐条列出，验收逐圈核对；进度量不能为了好看而放弃真实缺陷。
7. **估算与硬预算**：`C` 为预计总圈数。初始估算可用 `ceil(待处理成员数 ÷ 真实切片实际处理数) × 2`；资格化和逃逸普查的工作分别计入；无人口里程碑可暂取 3，交付取 4。写明实测依据、尚未验证的假设与下一次核对点，不能把扫描数当作实际处理数。后续实测推翻估算时，由独立评审修正方法、批次、里程碑或剩余圈数，不为符合算式扩大设计阶段。用户明确给定的费用、时间或圈数限额单独列明来源和已用量，不能随估算上调；未给出的硬预算不得从 `C` 推定。

设计需要精确行为（分类、取值表、逐条规则、真值表）时，不用文字或表格承载，交给 `reference/` 下一个可执行参考（原型函数及其判别用例集，或最小契约测试）作为唯一权威，正文只陈述决定并引用它。参考出错按「缺陷复盘」第 8 条区分交付物缺陷与辅助验证缺口，不能仅因它是可执行参考就归为实现缺陷。

写入设计的关键技术主张（按返工检验属于立项期义务的主张：某个接口、注入路径或观测量是否存在，某个迁移能否在既有数据上执行，某个判定器能否在真实人口上运行并对未知失败）由写入它的会话在同一轮用最小验证实验证明并引用实验输出。实验必须运行真实代码路径（导入生产函数、使用生产 schema 或 DDL，或在真实环境中执行）；手工转写源码逻辑的模型不算。实验不属于重型任务，不以负载或时长推迟；确实无法执行时该主张不写入设计，改用能够验证的方案。关于全体对象的主张不由实验证明，由契约的运行计数陈述。

### 评审条件

评审只审决定登记、风险清单、验收契约与圈计划，不审文档是否写到了实现细节。

**通过**的四个条件，全部满足即通过，与评审是否还有意见无关：

1. 决定登记中没有未反驳的阻塞问题。
2. 每条核心目标有验收契约，字段齐全，残余容忍与 Task「价值判断」一致。
3. 每份契约在真实切片上运行过一次，有计数与测得的单位成本。切片须覆盖它所声称验证的完整路径，不能把局部裁定或扫描的吞吐当作完整验收的成本；尚未验证的部分列为风险，按返工检验决定何时消除，不要求立项期建完全部判定器或枚举全人口。圈数估算使用这些数字并标明假设，硬预算与估算分开。
4. 风险清单中每条风险有消除方式，按返工检验属于立项期义务的已退休；第一个里程碑是竖切片。

**阻塞问题**必须同时写明两项，缺一项的是注意事项：它攻击的对象（某条 `D-n`、某份契约的某个字段、某条 `R-n`、某个里程碑的划分或顺序）；它的后果：按返工检验的四种返工之一，或某条核心目标不可达，或该决定与 Task 明文约束、项目权威规则冲突，或某条关键技术主张没有验证或验证不真实（没有运行真实代码路径、没有覆盖该主张、结果不支持结论）。

以下不是阻塞问题：判定器定义完整时某个成员未列出、信任基之外的写法、归类规则的细节；契约运行结果中的失败与未知；设计中已写明理由的取舍与范围判定（只有给出理由不成立的新证据时才重开）；本轮未改动且已有结论的决定。注意事项记入账本（类别 `note`），不阻塞，不写入设计，实现期由验收发现。

**转换规则**：分析不能解决的阻塞问题由再设计转为风险清单的一条，写明消除它的里程碑、分支与触发条件；转换后该问题闭合。这不是推迟：推迟是不处理，转换是预先定好用什么证据、在哪一圈、走哪条分支解决。按返工检验属于立项期义务的问题不得转换。

**设计范围**以 Task 的编号要求和其它明文约束为界。修正范围内对象的事实错误、矛盾、可执行性与可验证性不算扩大范围。只有两种情况可以把新对象纳入设计：缺少它会直接使某条 Task 要求的验收条件或 Task 写明的目的不能达成（写明要求编号与失败方式）；范围内对象改为判定器的人口，由此列出的成员随之纳入（只改变表达方式，不纳入新类别）。范围外的发现记入账本（类别 `out-of-scope`），由再设计按「缺陷复盘」第 8 条登记，不写入设计。

### 复评与停止

验收判断实际进展明显低于预期、上一圈的预期没有兑现且原因不在下一圈可修复的局部、方案被证伪、进度量失真、同类失败反复出现或估算不再可信时，交给已有的独立评审者。复评回到用户目标，根据整个任务（全部核心目标与里程碑）的实际执行、成果、失败和投入，独立判断当前推进方式出了什么问题，以及怎样继续最有价值：**现在是否存在一个有依据、值得继续执行的下一步？** 先读运行记录中历次预期的核对结果，以它判断以往判断的可靠程度。重新考虑方案、工作组织（里程碑顺序、拆分与并行）、验收方法、附加要求、进度量和估算；历史方案、评审结论与继承义务都是证据，不预先假定它们仍然正确，也不把判断限于本次差异或当前里程碑。围绕造成停滞的关键约束与假设作出判断，不要求逐项重审全部历史义务。只补足判断所需的证据；分清已实际执行与仅被派发的动作。多次再入不是自动停止条件，也不是自动续跑的理由。

- **继续**：对照实际成果、投入与原预期的偏差，说明当前方法为何仍有效，或应修正哪些假设、指标或方法；写明具体下一步、支持它的证据、下一圈结束时可以二元判定的预期结果（一到三条）与预计投入，以及如何核验。上一次复评的预期没有兑现时，先说明原因，以及这次判断的依据与上次有何不同；不能只增加圈数或重述待办。批准的下一步应足以产生可判断的成果，不以「做完一小批再复评」代替判断。首次完整成功或取得合格成本样本不是复评前提；成本不确定时如实保留不确定性，用已有产出与投入作判断。原因尚不清楚但有值得执行的最小判别实验时，该实验可以成为下一步。评审可直接修正计量、估算和计划；需要实质技术再设计时交作者处理，再由评审核验，不替作者实现。只修改受新证据影响的部分，保留有效成果、历史记录及经复评仍成立的义务。
- **停止尝试**：尚不能证明目标不可达，但找不到有依据且值得执行的下一步，或用户的硬预算已经耗尽。保存成果、失败方法、剩余工作和恢复所需条件，`status: 停止尝试`。证据表明继续确实需要改变用户目标、质量或硬约束时，写明具体约束、证据与建议，交负责人决定；普通未完成项不因此要求负责人降低要求。停止一次尝试不等于目标不可实现。
- **不可实现**：有目标层面的证据证明某条核心目标在明确约束下不可达，例如真实实验揭示无法绕开的限制，或准确引用加具体反例证明约束矛盾。写明证据为何排除了满足目标的路径；某种实现失败、旧估算被超过、进度量不动、再入次数多都不足以支持此结论。

独立评审可撤销不必要的附加要求、替换失效的证明方式、调整里程碑归属；按共同原则 5 判断它保障的结果与质量，不以提出者、文档位置或历史触发次数决定必要性。替换后仍须判断原目标要求的性质、覆盖原对象、满足原残余容忍，未知不冒充通过；仍有效的目标与质量要求所对应的缺陷须能检出，只检验已撤销方法或格式的旧对照可有据修改或撤销。说明新方式为何足以验收，取舍写入设计，保留旧结果及理由；受验证错误影响的结论须重新核验，不能恢复未经证实的通过。对原因未明、当前未再现的历史失败，可依据已有调查、当前验证和剩余风险决定结束调查、不再阻塞；在评审记录中保留失败事实、未知原因与处置理由，不把未复现写成已修复。已确认违反目标或质量要求的缺陷仍须修复并验证。修正不要求先证明目标不可达或绝对无风险。

评审不得扩大用户授权或提高用户硬预算。`C` 与立项吞吐是可修正的预测。任何会话在执行会突破明确硬预算的工作前均应停止尝试，记录已用量与约束来源，不以复评或等待为由突破它。

修改设计先 `snapshot review-c<c>`；换进度量用 `progress redefine`，在 `retro.md` 写明旧定义与换量理由，新口径必须有实测初值，旧数值不跨口径比较。复评结论追加进评审账本与 `retro.md`，包含继续或终止的证据；不另建裁决角色或轮询任务。

### 运行记录

每轮在 `retro.md` 追加一条，只写：轮次与角色；本轮结论；对上一轮预期的逐条核对（命中、未命中或无法判断，及证据位置）；本轮写下的预期与预计投入（作出继续或接受下一步的角色写）；关键证据位置；下一步。不复述未改变的状态、计数与历史；交接只记录新会话的标识与读回的参数。

任务终止时补充总结，只记录可核对事实：终止状态和原因；立项轮数、圈数、各里程碑最终状态；预期核对的命中情况；账本中阻塞问题、注意事项、驳回与转换为风险的数量；再入次数及其原因；验收发现的实现缺陷数与验证缺口数，逃逸类别分布，各「机制·模块」与完成的结构性修改；进度量的完整序列；主干既有缺陷及其登记情况；运行中对编号要求作出的全部取舍、理由与证据位置；是否发生人工介入（按本文件正常运行时应为 0）；对协议的改进建议，最多三项，并说明对应证据。

### 立项

你是立项者，也是独立评审要求再入时的再设计者。先读状态头判断进入方式。

**首次进入**（设计文档不存在）：

2. 按「设计文档要求」写出七部分。风险清单先列后排：对每条风险按返工检验判定它是否立项期义务，是则本轮用最小验证实验退休，否则写明消除它的里程碑与分支。每份契约在一个真实切片上运行一次，记录计数、单位成本与处理的成员数；第一个里程碑按共同原则 7 竖切。

### 工作轮

你是工作轮，与验收轮交替执行。深度理解设计文档，按以下流程执行：

1. 读状态头的 `next-step`，执行它，不自选工作。`next-step` 指向某条风险的消除时，产出是退休该风险的实验或切片及其证据；指向某个里程碑时，只推进该里程碑，完成它所必需的测试、脚本、环境配置和缺陷修复都属于本轮。验收记录「下一步要达成的结果」有内容时先完成它，并以其中的预期检查自己的进展。
2. 竖切地造：先在一个真实切片上端到端跑通，再扩人口。优先复用项目测试体系；修复真实缺陷时先建立能够失败的复现，再修复并运行通过。
3. 运行受本轮改动影响的验收命令与契约判定器，把运行输出放进 `evidence/cycle-<c+1>/`，记录计数；准备标 `待审` 时运行当前里程碑列出的全部验收命令与契约。资源暂不可用时先执行「资源等待不结束轮次」。
4. 发现决定被证伪、估算失准或进度量不能表示剩余工作时，记录证据并提案复评或换量，不自行改目标或计划。已有风险分支仍适用时可提案采用；契约定义缺陷写明需修正的字段与重跑方法，交验收确认；非核心要求的冲突交验收按共同原则 8 取舍。
5. 执行受本轮修改影响的项目基础检查。任务开始前已经失败的检查以基线记录为准；不得新增失败，也不得以同名旧失败掩盖不同的新原因。
6. 标 `待审` 前先自检：用契约的同一人口权威派生至少一个不在本轮改动目录内的变体（删去一个成员、加回一条第二路径或改写一个缺省），对它运行验收与判定器，变体应红、还原后应绿；自检发现的缺陷在本轮修复并写入证据，不交验收去发现。自检通过且验收通过时把里程碑标为 `待审` 并记录命令、结果、自检变体与证据；未通过时保持 `开放` 并记录具体阻塞。不得标记 `已完成`。
7. 在验收记录末尾写「工作轮提案」段：本圈做了什么、实际投入、对照本圈预期的完成情况、进度量的本圈值及其来源、下一步提案（哪条风险或哪个里程碑的哪一步，为什么），以及第 4 条中的复评或换量提案。
8. 确认「资源等待不结束轮次」允许结束本轮后，追加本轮记录到 `retro.md`，**一律**使用 `Please execute {{DOC_DIR}}/{{SLUG}}-task.md 验收轮.` 作为 prompt 启动新的 chat（无论你认为完成与否，都交给验收轮判定，不自行连续启动工作轮）。只要启动就可以结束，不需要等待。**使用 `{{SESSION_SKILL_ACCEPT}}` 中的方法来启动新的 chat{{SESSION_ARGS_ACCEPT}}。**

### 验收轮

你是独立验收者，与工作轮交替执行。不得信任里程碑状态或工作轮的结论；你判增量、判提案、判进度，不写实现方案。按以下顺序执行：

1. 先核对上一圈写下的预期（验收记录「下一步要达成的结果」中的预期与预计投入）：逐条判命中、未命中或无法判断，写明证据。然后复验受本圈改动影响的验收命令与契约判定器，以及本圈修改可能影响的已完成里程碑，其余按风险抽查；工作轮标 `待审` 时，执行该里程碑列出的全部验收命令与契约运行。资源暂不可用时先执行「资源等待不结束轮次」。验收报告的失败按「缺陷复盘」第 8 条判断是否阻塞。
2. 对照 Task 要求（按设计中经取舍的口径）、设计和代码差异对真实实现做对抗性审查。以具体输入发现漏检时，先把该输入交给对应的判定器运行：判定器报告失败或未知的，是未完成的工作，写入「下一步要达成的结果」；判定器在信任基内静默放过且修正需要改动契约定义的三部分之一（人口来源、未知分支、信任基）的，是契约定义缺陷：写入「下一步要达成的结果」，由下一圈工作轮改定义一次并重跑人口，重跑后的那一圈由验收以 `progress redefine` 记新口径与实测值；同一契约反复修正后仍不能可靠判定时提请复评。在信任基之外的，不是缺陷，记入残余。判定器报告须按目标与证据核验，区分真实未完成项与判定器误报，不能因报告失败或未知就把所用证明方法变成目标要求。阻塞性问题必须附可复现失败、测试输出或明确的代码证据。
3. 区分两类问题。**实现缺陷**：要求交付的产品能力或对象不符合设计中有效的要求或 Task，建立失败复现，按「缺陷复盘」写缺陷卡片并判断是否阻塞，阻塞的使里程碑恢复为 `开放`；主干既有缺陷按第 6 条另行登记，不阻塞的按第 8 条登记、不恢复里程碑。一个问题同时暴露产品错误与验证错误时分别处理。**验证缺口**：验收方法、辅助检查器或证据不足以支持结论，包括漏检、误报与辅助验证错误；修复或有据替换验证方式，完全还原临时缺陷注入，再立即复验受影响结论。验证缺口不算实现缺陷，不自动触发结构性修改；确实改变契约定义的按第 2 步换量。产品复验通过时不因验证加强而退回；旧通过结论失去依据时保持未通过，直到重新验证。缺陷注入只应移除、短路或替换生产路径以验证判别力，判别力作为全称性质时按契约的资格化方式全量验证；不得制造虚假的生产副作用。
4. 判断复现：本圈卡片中有与当前里程碑既有卡片相同的「机制·模块」时，按「缺陷复盘」第 4 条判断原因是否在结构上，并把结论写入卡片；在结构上的，把结构性修改写入完成条件。
5. 记录进度：本圈进度量的值由自己复跑或重算得到（不采用工作轮报告的数字；C 类指重算裁定记录的计数并复验抽样样本），`progress append <value>`；进度量反映不了剩余的完成条件时用 `progress redefine` 换量，并在 `retro.md` 写明旧定义与理由。
6. 按验收结论更新里程碑：验收通过且没有阻塞的实现缺陷，`待审` 标为 `已完成`，`milestones` 加一，该里程碑退休的风险在清单中标 `已退休`，`risks` 更新，`current-milestone` 改为下一个未完成里程碑，并以该里程碑进度量的初值 `progress redefine`；否则里程碑为 `开放`。
7. 判提案与下一步：对照上一圈预期的核对结果、近期保留下来的有效成果与实际投入，判断工作轮的下一步是否仍值得执行，以证据接受或否决，不以偏好替换。进展略低于预期但方法仍有证据支持时可以继续；明显低于预期、预期未兑现且原因不在下一圈可修复的局部、反复返工、数值反复回落后仅恢复旧成果、方案被证伪、进度量已到终点却仍有范围内义务、同类失败反复出现或估算不再可信时，提请复评。修复关键缺陷或消除风险可构成有效成果；仍有未完成项、局部计数改善或没有新实现缺陷本身不足以支持继续。接受下一步时写明下一圈结束时可以二元判定的预期（一到三条）与预计投入。
8. 覆盖写入 `{{DOC_DIR}}/{{SLUG}}-acceptance.md`，保留四个常设段落：**未闭合缺陷**（卡片摘要、阻塞判断与当前失败证据）、**根因与范围**（逃逸证明、逃逸类别、同类普查、复现判断与第 8 条依据）、**下一步要达成的结果**（只写要成立的不变量、输入范围、判定标准、完成条件，以及下一圈的预期与预计投入；不写实现方案；不阻塞与已分配的只列去向）、**门禁**（当前应红、完成应绿、不得退化的命令，缺口类门禁使用判定器的人口）；末尾保留工作轮提案段供下一圈覆盖。
9. `cycle advance`，`state set next-step` 为接受的下一步；需复评时写「复评：<原因与证据>；恢复点：<当前里程碑与状态>」，追加本轮记录到 `retro.md`。
