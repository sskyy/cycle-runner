### 共同原则

1. **产品结果优先**：下列规范用于促进任务完成，不得为了完善流程文件而延迟主要工作。
2. **证据优先**：涉及代码现状、运行行为或外部接口的判断，应优先使用源码、现有测试、实际命令或最小验证实验。纯逻辑矛盾可以使用准确引用和具体反例证明。
3. **一次处理同类问题**：评审与审计的问题必须说明根因和检查范围，并列出该范围内全部同类问题；裁决或修复时再次检查同类位置，一次处理完毕。同类按被违反的规则（Task 要求、设计条款或项目规则）认定，不按表面写法或位置；它的成员由判定器列出。判定器由三部分定义：**人口**从结构性权威关系派生（类型、符号引用、注册表、生成物、文件全集、语法树节点种类全集，或本任务改动、要求处理的对象的全部内容，按文件、模块或记录整体计，不按改动的行）；**归类**带缺省分支，不能识别或需要判断而未判断的成员一律判「未知」并失败；**信任基**写明人口与规则语义之间依赖的前提，只允许平台有文档的语义和仓库中已在运行的门禁，其它前提在本任务内各自给出检查。手写清单、按选定模式检索或以选定探针得到的列举，以及没有未知分支或没有信任基的识别机制，都不是判定器。成员的归类结论由判定器运行得到并记录在机制中（登记表、普查结果或证据文件），后续轮次只审新增或改动的成员；改判已有结论须给出新证据（可复现的失败，或准确引用加具体反例）。判定器定义缺少三部分之一时，它漏掉的成员不论在哪一轮、由哪一方找到，都是同一个问题，修正是补全定义；补列被找到成员的形式或位置（词表、句型、模式、扫描轴、站点）不是修正。定义完整后，运行报告的失败与未知是待完成的工作，某个成员归类错误是单个问题；信任基之外的写法只有在代码中存在真实实例且该实例违反规则时才是问题，否则记入残余。只能靠语义判断的类别（例如注释与文档中的陈述）没有判定器：成员集合是本任务改动或要求处理的对象的全部内容，以及引用这些对象的位置；能改为引用权威的删去副本，其余逐一审完并记录结论，按「设计文档要求」第 2 项的语义转换验收。同类只在任务的作用范围内认定（设计期见「设计复审条件」的设计范围，实现期见「缺陷复盘」第 8 条），不得以同类为由把范围外的对象纳入本任务。
4. **设计只对决定与判定器定义负责**：设计以编号决定确定方案、事实的归属（唯一写者与位置）、里程碑的划分、顺序与接口、范围取舍和验收口径，并用实验证明关键技术主张；对每条涉及全体对象的要求，设计给出判定器定义或语义转换。设计期证明的是可行性与定义：全称性质的结果由判定器在真实人口上运行确立，设计期运行一次得到通过、失败、未知的计数与单位成本，失败与未知归零是实现期的工作。设计不写到算法与逐条规则的细度。问题只在满足「设计复审条件」的判据时才阻塞设计，其余由实现期的验收发现。
5. **验证采用项目原有体系**：优先使用项目已有测试、合同、运行脚本和真实环境。只有任务确有需要时才增加专用验证程序。
6. **协议版本固定**：本次运行始终使用本文件中的规则，不得在运行中同步其它版本。
7. **会话自主性**：设计、评审、实现和审计分别在独立会话中完成。各会话不得向用户询问如何继续；遇到未明确规定的事项，应依据任务目标、项目原则和已取得的证据作出合理决定，并记录理由。Task 的核心目标不得放宽；其它编号要求只在按原文不可达、与其它要求或项目权威规则冲突，或按判定器运行结果与单位成本估算的工作量在实现预算内不可完成时，由裁决轮（实现期由审计轮）以最小偏离作出取舍。取舍须有证据（最小验证实验，准确引用加具体反例，或计数与单位成本的估算），按「设计文档要求」写入设计；代价大本身不是取舍的理由，经测量超出预算的工作量是。

### 资源等待不结束轮次

本节适用于所有阶段，先于计数、结束和启动下一 session 的步骤执行，最后一个预算轮也不例外。本轮必需验证因执行资源暂不可用而未运行或中断时，必须在当前 session 内使用等待工具等待，资源可用后继续执行；不得因等待结束 session、增加 `d`、`k` 或 reopen、启动下一 session，或判定任务失败。

优先使用项目已有的排队机制，遵守资源准入规则。等待工具单次返回或排队命令超时不代表等待结束：检查原进程，仍在排队或运行则继续等待，已因排队超时退出则在同一 session 重新排队，避免重复启动。没有排队入口时，用等待工具分段等待并复查准入条件。资源恢复后复核代码与环境，补跑缺失或已失效的验证；实际执行后发现的失败按原缺陷协议处理。

只有用户明确停止或宿主强制中断时，才在已有 `retro.md` 保存当前轮、已完成工作、等待资源、进程与待执行命令，不自动交接；恢复后核对状态并继续同一轮。不得自设等待时限作为中断理由。已证实的其它技术或权限问题仍按原取舍与终止规则处理。

设计文档开头必须维护：

```text
status: 设计中 | 实现中 | 已完成 | 不可实现 | 协议失败
design-round: d/15
implementation-round: k/N
current-milestone: M-xx
current-milestone-reopens: r
convergence-mode: normal | domain-review | milestone-review
next-action: <下一实现轮首先完成的具体工作；没有时写“无”>
```

计数规则：

- `d` 由设计裁决轮在满足「资源等待不结束轮次」后增加，设计评审轮不增加。
- `k` 由实现轮在满足「资源等待不结束轮次」后增加，审计轮不增加；等待及恢复同一轮不额外计数。
- `r` 是当前里程碑因实现缺陷从 `待审`退回`开放`的累计次数；验证缺口直接加强后产品仍正确、或里程碑本来就是`开放`时不增加。
- 设计完成时，以初始里程碑数量 `M` 计算 `N = 5 × M`。这是所有里程碑共享的总预算，不设单个里程碑预算。
- 实现中可以调整未完成里程碑，但 `N` 不随拆分或合并而改变。

里程碑状态只有：

- `开放`：尚未完成。
- `待审`：实现轮已取得通过证据，等待独立审计。
- `已完成`：审计轮独立复验通过。

实现轮不得将里程碑标记为 `已完成`。

#### Reopen、缺陷复盘与收敛

设计文档中每个里程碑还必须维护 `reopen-count` 与 `defect-mechanisms`：

- `reopen-count`：审计确认实现缺陷并把该里程碑从`待审`退回`开放`的次数。纯验证缺口、原本就是`开放`的里程碑不计。
- `defect-mechanisms`：以「根因机制·模块」为键的计数。审计轮每确认一个范围内的实现缺陷（「缺陷复盘」第 8 条），就为它的键加 1（同一审计轮同一个键只加一次），不论里程碑原本是`待审`还是`开放`。机制只能取「缺陷复盘」中的机制词表；模块写项目的规范模块根。可以附简短说明，说明不参与计数，也不得通过改写说明或改换模块写法规避升级。

旧任务首次采用本机制且缺少计数时，下一审计轮根据 `retro.md` 中该里程碑真实的审计记录初始化。

触发规则：

- 某个「机制·模块」计数达到 2：`convergence-mode: domain-review`，对该机制执行完整复盘。
- 同一里程碑 `reopen-count` 达到 3：`convergence-mode: milestone-review`，对该里程碑出现过的每个机制执行完整复盘。
- `milestone-review` 优先级更高；收敛模式一旦触发，直到里程碑关闭前不得恢复为 `normal`。之后又有机制计数达到 2 时，同样对它执行完整复盘。

触发收敛模式的审计轮必须在当前实现审计文件顶部维护 `## Convergence Note`，不得新增流程文件。Note 只记录尚未闭合的差异，不复制 Task、设计正文或完整历史，并固定为四部分：

1. **Remaining closure map**：未闭合的「机制·模块」、对应缺陷卡片的摘要及当前失败证据。
2. **Root cause and scope**：完整复盘的结果：逃逸证明、逃逸类别、来自权威来源的同类普查，以及前轮为何漏检。
3. **Next implementation batch**：按依赖顺序写出下一轮必须达成的结果：要成立的不变量与结构性质、输入范围与判定标准、完成条件。只写要达成什么，不写实现方案（见「缺陷复盘」第 5 条）。只列范围内且未分配的完成条件；范围外与已分配的缺陷只列登记位置或去向（见「缺陷复盘」第 8 条）。
4. **Closure gates**：当前应红、完成应绿以及不得退化的命令，包括结构性质的机检命令与缺陷注入方法。缺口类门禁使用判定器的人口（共同原则 3；对尚无实例的形式而言，人口来自定义该形式的文法或规范），不得以手写列举或审计发现缺口时使用的探针代替。普通模式下，`next-action` 中的完成条件同样适用本款。

后续审计覆盖写审计文件时必须保留并更新该 Note，直到里程碑关闭。`next-action` 应简短指向 Note 的下一实施批次；`retro.md` 记录 reopen 次数、各「机制·模块」计数、收敛模式、完成的结构性修改及关闭轮次。

#### 缺陷复盘

审计确认的每个实现缺陷都按以下方法复盘。项目画像给出「缺陷复盘协议」（机制词表、逃逸类别细分、逃逸证明工具、主干既有缺陷的登记流程）时，使用项目画像中的词表与工具；没有给出时使用本节的默认词表和方法。

1. **缺陷卡片**：每个实现缺陷在审计文件中写明现象、证据、根因机制与模块、在任务基线 revision 上能否复现、逃逸证明、逃逸类别、同类普查和补救。
2. **逃逸证明**：在缺陷修复前的代码上运行实现轮声称通过的验收命令，以及离缺陷最近的既有测试，记录结果属于哪一种：未执行、执行但看不到失败、失败但被忽略、不存在相关测试。
3. **逃逸类别与补救**：
   - **A 验证体系缺陷**：相关验证没有执行、被跳过、判定条件看不到失败，替身、夹具与真实实现不一致，或判定器定义缺少三部分之一而在信任基内静默放过。补救是修复验证机制本身（接线、取消跳过、修正判定条件并加正向对照、替换失真的替身、补全判定器定义），不只是增加一个用例。
   - **B 用例不足**：验证机制正常，但缺少维度或实例。补救是按共同原则 3 以判定器（人口来自注册表、生成物、状态机、类型定义或可执行普查）列出全部同类实例，并扩展模型、参考函数或输入生成器；只有确实没有可用模型时才补充单个用例，并写明理由。
   - **C 其他**：设计没有定义该行为、缺陷位于第三方或框架等。写明需要的设计裁决或上游修复。
4. **完整复盘与结构性修改**：某个机制触发收敛时，对它的全部缺陷执行逃逸证明与同类普查，并要求下一实施批次做出使该机制在结构上不能再发生的修改，例如一个事实只有一个写者或读者、从权威来源派生、类型化的载体、统一的参考函数。对同一事实存在多个副本、多个写者，或多处各自推导同一事实的机制（如多副本漂移），结构性修改必须使该事实只剩一个写者和一个推导位置：删除其余副本、写者或推导，或把它们改为调用同一个从权威来源计算的函数。比较、校验或普查副本之间是否一致的检查属于验证补救（A 或 B 类），不算结构性修改；保留副本而增加检查的，不满足本条。结构由实现轮设计，并同步修订设计文档中对应的方案。审计按三项验收：结构性质由判定器机检（共同原则 3）：类型、模块边界，或从权威来源列举全部写者与读者的契约测试；多副本类机制须由可执行的普查列举该事实的全部写者与推导位置，且各恰好一个；只识别已列出形式的检查不算。人为加回第二条路径（第二个写者或读者、手写副本、未类型化的字段），或以检查未曾列出的写法加回时，测试变红；逃逸类别要求的验证补救已经完成。结构完成之前，同一机制的新实例照常认定为实现缺陷。只能靠语义判断的类别没有可机检的结构性质：结构性修改是在共同原则 3 所说的成员集合中删去副本或改为引用权威，验收是对该集合逐一审完，并按「设计文档要求」第 2 项的语义转换终止。
5. **审计只写要达成什么**：审计可以用候选修改验证可行性，但候选修改不属于实施批次；实现轮自行设计实现，与审计的可行性验证不同时说明理由。
6. **主干既有缺陷**：在任务基线 revision 上能复现的缺陷不是本任务引入的。先按第 8 条判定作用范围：范围内的在本任务中修复，范围外的按第 8 条处理；两者都按项目画像的缺陷复盘协议登记，画像没有规定时在 `retro.md` 中单独列出。本任务引入的缺陷只记录在审计文件中。
7. **超出任务范围的修改**：结构性修改需要 Task 明确排除的改动（例如 Task 规定不改的协议或框架）时，按 C 类写明需要的裁决或上游修复，并按项目的 issue 规则建立后续任务。该缺陷若违反 Task 要求或里程碑验收，里程碑仍不能关闭。
8. **作用范围**：审计对每个缺陷（包括记为备注但已复现、或有明确代码证据的偏离），以及里程碑验收报告的每个失败，判定它是否在当前里程碑的作用范围内，并在缺陷卡片中写明依据。
   - **对象**：缺陷所在的内容（代码、数据、文档或配置中出错的那部分）。以缺陷被发现时为准：修一处即可消除全部位置的，是同一根因，任一位置在范围内即整体在范围内；需要分别修改的多个位置，是同一机制的多个实例，逐个判定。
   - **范围内**，满足下列任一款：
     - (a) 缺陷使当前里程碑某条覆盖要求或结果所陈述的行为、取值或结构性质（例如「全部查表」「只有一个写者」）不成立；或者缺陷所在内容包含于这些要求或结果要求创建、修改或修复的对象之中（例如要求修改一条记录，则记录中的任一句）。只要求阅读、确认或报告的对象不因此进入范围，对其正确性的要求按行为判据判定。要求以文件路径指明对象的位置时，对象是该位置上被要求处理的部分，不是整个文件。结果要求创建的交付物（例如一个 PR）只纳入其中为实现该结果的内容。为说明依据、约束或排除而提及的对象不算；验收命令不扩大本款的对象。以类定义的对象（例如「同类写法」「每条红灯」）指从权威来源枚举出的成员，卡片写明枚举来源；无法枚举时按本款的行为判据判定。
     - (b) 缺陷由本任务的改动造成，在任务基线上不能复现（任一里程碑、任一轮次）。
     - (c) 在缺陷被发现之前，本任务为实现当前里程碑的结果而新建或修改了缺陷所在的内容，包括为范围内对象编写的测试、检查器与证据。
   - **范围外**：不满足上述任何一款。为修复、登记或检查范围外缺陷而做的新建或修改（包括登记条目、证据，以及检查范围外对象的检查器）不使对象进入范围，这些内容上的缺陷与失败同样在范围外，不需要基线运行；其中由本任务造成的记在审计文件中，由项目画像的登记流程修正。本任务新建的检查器漏检时，按它漏检的对象判定；尚无实际漏检实例的形式缺口按下一款判定。
   - **同时服务范围内与范围外对象的内容**（例如检查器的人口同时包含两类对象，或一条登记条目同时登记两类缺陷）：按出错部分已经造成误判、漏判或误述的对象判定：涉及范围内对象的在范围内，其余在范围外；同一处错误同时涉及两类对象时按范围内。尚无实际漏检实例的形式缺口，只有范围内对象的现有内容含该形式时才在范围内。
   - **优先级**：(a) 优先于范围外一款的排除句；排除句优先于 (b)、(c)。
   - **归属与分配**：
     - 一个对象在多个里程碑的范围内时，结果有区分的，按缺陷违背的那句结果所属的里程碑；没有区分的，归其中尚未完成、编号最小的里程碑。已完成的里程碑不重新打开；归属于已完成里程碑的缺陷，归当前里程碑。
     - 范围内的缺陷可以分配给后续里程碑或独立 issue，条件是二者之一：该缺陷存在时，后续里程碑的结果陈述不能成立（只要求登记记录的句子，例如「记录写成 closed」，不算）；或经负责人确认的变更作出该分配。实现轮按模板修订未完成里程碑的结果后，以修订后的结果判定。审计写入设计文档的备注本身不是分配依据。原因未定位的失败同样适用本款。审计在卡片中写明分配及其依据；未分配的范围内缺陷是当前里程碑的完成条件。
   - **范围外缺陷的处理**：审计逐条写出核对过的要求编号与结果句子，以及不相符的理由；按项目画像的缺陷复盘协议登记（缺陷条目、仍失败检查的 owner 与期限、后续 issue）。它不成为本里程碑的完成条件，不计入 `reopen-count` 与 `defect-mechanisms`。登记不等于机制闭合：同一机制在范围内再出现时照常计数。
   - **验收中的失败**：里程碑验收报告的失败（包括结构性质的检查、整条测试 lane、全量测试、远端 CI 与退出码类判据）同样按本条判定。
     - 原因已定位到内容的失败按缺陷判定；竞态定位后按参与竞态的代码判定。以下各款只用于原因尚未定位的失败，其对象是失败的检查所检查的对象。
     - 基线是不含本任务任何改动的检出（优先当前主干，无法运行时用任务基线 revision），在同一机器与同一配置上实际执行同一检查；本任务新建的检查叠加到基线检出上执行。合入了本任务提交的分支、代码阅读与 `git blame` 都不是基线运行。
     - 失败所在对象不在范围内时，审计取得基线运行结果。基线上的执行次数（同一检查在同一条件下的执行次数）不少于分支上；同样出现（包括间歇出现）的，为范围外，按上一款登记，不阻断本里程碑，也不因「不得新增失败」或整体退出码成为完成条件。在取得基线结果之前，或基线上不出现的，该失败在范围内。
     - 环境失败指机器状态或外部服务造成、与本仓库代码无关的失败，须有证据：同一修订在环境恢复后通过，或错误直接指向机器状态或外部服务。只在负载或特定交错下出现的竞态是代码缺陷，按对象判定。单独重跑通过既不是基线运行，也不是环境证据。环境失败不是缺陷；在取得环境正常的运行结果之前，对应验收视为未执行。
     - 范围内的失败阻断验收，未分配时一直是完成条件；里程碑因此不能完成时置为`开放`，但不计入 `reopen-count`，定位为实现缺陷后才计入 `reopen-count` 与 `defect-mechanisms`。
     - Task 要求对失败的处理另有规定时，以 Task 要求为准。
   - **无法判定时**：按本条仍无法判定的，按范围内处理，卡片写明无法判定的原因。
   - 除 (b) 款与失败的基线归因外，判定不看缺陷能否在任务基线上复现，也不看它与范围内缺陷是否属于同一机制。
   - 范围内且未分配的缺陷是当前里程碑的完成条件：不论能否在任务基线上复现，都在本任务中修复，计入 `defect-mechanisms`，里程碑为`待审`时计入 `reopen-count`，并按本节触发收敛与结构性修改。
   - 卡片的依据栏：(a) 写要求编号或结果句子，以及不成立的行为或包含它的对象；(b) 写引入它的提交或轮次；(c) 写新建或修改该内容的提交或轮次；分配写去向与依据；范围外写核对过的要求与结果及理由。

### 设计文档要求

设计文档应包含：

1. **背景和现状**：只写与任务有关的事实，并给出代码、文档或运行证据。
2. **目标与非目标**：逐项对应 Task 的核心目标与编号要求。涉及全体对象（全部、每个、任一）的要求写明确立方式，二选一：**判定器**（引用第 5 项中的定义与运行结果）；**语义转换**（没有判定器的类别：先结构化，把文本改为从数据派生或引用唯一来源，使它成为判定器可判的性质；做不到时写明固定人口、单位成本与验收抽检；单位成本由实际复核一个样本测得，不得估计）。经裁决缩小对象范围的取舍写在该要求下，缩小后的对象仍由判定器列出。验收抽检的默认标准：人口逐一审完并记录结论后，审计轮按记录的随机种子抽取人口的 10%（不少于 30、不多于 200，人口不足 30 时全查）逐个复核；样本中任一错误按共同原则 3 连同其同类一并修复，然后换种子重抽；一次全样本无错误即通过。项目画像的缺陷复盘协议可以覆盖样本量。经裁决的取舍与范围判定写在对应要求下：取舍后的口径、理由与证据位置，只写当前结论；裁决改变取舍时改写该处。
3. **决定登记**：只保留一个明确方案，拆成编号决定 `D-01..D-n`，每条写结论、理由与证据位置；设计正文其它位置引用决定编号，不重复陈述。被驳回过的异议在该决定下记一行结论，再次提出须有新证据。
4. **里程碑**：按依赖顺序编号为 `M-01..M-N`。
5. **判定器与验证安排**：每个判定器写三部分定义（共同原则 3）和一次真实人口上的运行结果：通过、失败、未知的计数，失败与未知成员清单的位置，单位成本（由实际处理一个样本的成员测得，复核或修复均可，不得估计）；由计数与单位成本估算完成全部成员的工作量并与实现预算对照，核对待处理成员是否都在 Task 允许修改的对象之内，超出预算或与 Task 约束冲突的按共同原则 7 在设计期取舍。区分设计期必须验证的风险和可以在实现期验证的风险，判别方法是返工检验：某个主张若在实现期被证伪，是否需要重做已完成里程碑的工作、改变方案或跨里程碑接口、执行或撤销不可逆操作，或使工作量超出预算；是则为设计期义务，否则由所在里程碑的验收发现。设计期答不了的量写明：该量、依赖它的决定、每种结果下预先定好的分支，并把消除它的工作排进最早的里程碑；按此安排的量不按「未验证」阻塞。
6. **基线**：记录任务开始时的 Git revision、工作树状态，以及与本任务相关的已有测试结果。

设计文档只陈述当前结论：每个决定、事实或规则只在一处陈述，其它位置引用该处；评审、裁决与修订的过程不写入设计文档（轮次记录写入 `retro.md`，实验输出放在任务目录的证据文件中）。裁决轮修订时改写对应段落，不在原文之后追加补充说明。

每个里程碑必须包含：

- 可独立观察的结果。
- 覆盖的 Task 要求编号。
- 前置里程碑。
- `reopen-count` 与 `defect-mechanisms`，初始分别为 `0` 与空集合。
- 验收命令；如果命令尚不存在，应准确说明实现阶段需要新增的测试或运行入口。
- 最新证据。

里程碑应当是可以运行和验证的阶段性系统状态。第一个里程碑应尽早消除最大的技术不确定性，其验收必须包含最小端到端链路跑通；每个判定器的失败与未知归零归入覆盖该要求的最早里程碑，归零之前该要求不算完成。

设计阶段采用精简的可执行验收：

- 每个里程碑至少有一个可执行验收入口或明确的待建测试。
- 并发、崩溃、切换、删除、权限和不可逆数据变更等高风险行为，至少提供一个能区分错误实现的负向对照或最小验证实验。门禁对某类改动的判别力（例如「删去任一接线，合同变红」）是全称性质，由变异判定器承载：变异算子集从权威来源派生（注册表、类型、生成物或语法树节点种类），全量变异并统计被检出的比例；评审者或审计自选的注入不能代替它。
- 关键技术主张由写入它的会话在同一轮用最小验证实验证明，并在设计中引用实验输出。关键技术主张指按返工检验属于设计期义务的主张：一旦不成立，方案或某个里程碑就无法实现或无法验收，例如某个接口、注入路径或观测量是否存在，某个迁移能否在既有数据上执行，某个判定器能否在真实人口上运行并对未知失败。实验必须运行真实代码路径（导入生产函数、使用生产 schema 或 DDL，或在真实环境中执行），并覆盖本轮写入的每一条关键主张；手工转写源码逻辑的模型不能作为证明（纯逻辑推论仍按共同原则 2 以准确引用和具体反例证明）。关于全体对象的主张不由实验证明，由判定器的运行结果陈述（第 5 项），设计期只要求计数与单位成本，不要求失败与未知归零。最小验证实验不属于重型任务，不以负载、时长等运行环境理由推迟；确实无法执行时，该主张不写入设计，改用能够验证的方案。
- 不要求为每个断言建立专用 schema、夹具集合或通用断言框架。

### 设计复审条件

只有满足下列任一判据的问题可以要求下一轮设计评审：

1. **决定不成立**：某条编号决定不能达成某条核心目标，或不能达成某条编号要求而设计中没有对该要求写明经裁决的取舍，或违反项目权威规则中的架构职责、数据原则或工程约束，或与 Task 的明文约束冲突（例如待处理成员落在 Task 禁止修改的对象内）；或按判定器运行结果与单位成本估算的工作量在实现预算内不可完成而设计没有相应的取舍；或某条关键技术主张没有验证，或验证不真实（实验没有运行真实代码路径、没有覆盖该主张、结果不支持结论）。
2. **修正会外溢**：修正它需要改变设计中其它部分依赖的内容：方案、里程碑的划分或顺序、跨里程碑的接口、不可逆操作（数据迁移、删除、对外发布）、范围或验收口径、预算。
3. **验证有盲区**：某条涉及全体对象的要求没有判定器定义也没有语义转换，或判定器定义缺少三部分之一（人口不来自结构性权威、没有未知分支、信任基未写明或超出允许的前提）；或对不涉及全体对象的行为，实现在该处出错时，里程碑的验收与审计轮对 Task 要求的逐项对抗性核对都不会发现。审计不以设计列出的注入、用例或探针为限。

三条都不满足的问题是实现细节：错误局限在一个里程碑内，计划中的验收会让它变红或审计会逐项发现，修正不改变任何编号决定或判定器定义。判定时问的是「该错误在实现期由哪项验收或核对发现、修正要改动哪条决定或哪个判定器定义的哪一部分」，而不是「设计是否写到了」。判定器定义完整时，评审找到的某个未列出或分类有误的成员、信任基之外的写法、归类规则的细节，都是实现细节，不论按哪条判据提出；运行结果中的失败与未知是归零里程碑的工作，不是复审问题。实现细节列为实现注意事项，只写在评审文件中，不阻塞设计，也不写入设计；评审文件每轮覆盖，注意事项不需要保留，实现期由验收与审计发现。注意事项指出设计中的事实错误时，裁决轮可以改正或删去该句，但不因此在设计中新增决定、口径或验收项。

设计范围以 Task 的编号要求和其它明文约束为界。修正范围内对象的事实错误、矛盾、可执行性与可验证性，不属于扩大范围。评审与裁决只有在以下两种情况下才能把新的对象或行为纳入设计：

1. 缺少它会直接使某条 Task 要求的验收条件或 Task 写明的目的不能达成。须写明该要求编号与失败方式。
2. 范围内的对象应当以体系化的方式表达，即改为判定器的人口（从类型、注册表、状态机、生成物或可执行普查派生）；由此列出的同类成员随之纳入。这只改变表达方式，不得借此纳入新的类别或 Task 要求之外的对象。

不得以逐项列举的方式纳入新的对象。设计期发现的、不属于上述两种情况的缺陷或改进，不列为需要复审的问题；由裁决轮按「缺陷复盘」第 8 条中范围外缺陷的方式登记，并在 `retro.md` 中写明登记位置。缺陷与改进本身不写入设计；裁决对 Task 要求所涉对象作出的范围判定，按「设计文档要求」第 2 项写入设计。

设计需要精确行为（分类、取值表、逐条规则、真值表）时，不用文字或表格承载，交给一个可执行的参考（原型函数及其判别用例集，或最小契约测试）作为唯一权威，设计正文只陈述决定并引用它。参考自身的细节错误、正文与参考之间的差异按实现缺陷处理，不作为设计复审问题；评审只按判据检查参考所承载的决定是否成立。
