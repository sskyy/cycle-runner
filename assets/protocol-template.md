### 共同原则

1. **产品结果优先**：下列规范用于促进任务完成，不得为了完善流程文件而延迟主要工作。
2. **证据优先**：涉及代码现状、运行行为或外部接口的判断，优先使用源码、现有测试、实际命令或最小验证实验。纯逻辑矛盾可以用准确引用加具体反例证明。
3. **主张按性质取证**：每种主张用最便宜的充分证据确立，不得要求更强的一种。**决定**（方案、事实归属、顺序、接口、取舍）靠论证加同一轮的最小验证实验。**全称性质**（全部、每个、任一）靠验收契约中的判定器在真实人口上运行确立：立项期只要求定义、一次真实切片上的运行计数与单位成本，失败与未知归零是实现期的工作。**语义性质**（只能靠判断的类别，例如注释与文档中的陈述）靠 Task「价值判断」中声明的固定人口、抽样策略与吞吐预算。判定器由三部分定义：人口从结构性权威派生（类型、符号引用、注册表、生成物、文件全集、语法树节点种类全集，或本任务改动、要求处理的对象的全部内容，按文件、模块或记录整体计）；归类带未知分支，不能识别或需要判断而未判断的成员判「未知」并失败；信任基写明接受而不证明的前提，只允许平台有文档的语义和仓库中已在运行的门禁。手写清单、选定模式检索与选定探针都不是判定器。某个成员未列出是实现细节；定义缺少三部分之一是契约缺陷，修正是补全定义并作为重新基线事件记录（共同原则 5），不是补列词表、句型、模式、扫描轴或站点。
4. **返工检验决定立项期义务**：某个主张若在实现期被证伪，会导致重做已完成里程碑的工作、改变方案或跨里程碑接口、执行或撤销不可逆操作、或超出硬上限，它才必须在立项期关闭；其余由所在里程碑的验收发现。立项期答不了的量不阻塞立项，写成风险清单的一条：该量、依赖它的决定、每种结果下预先决定的分支，并排进最早的里程碑用造的方式消除。
5. **冻结与重新基线**：立项通过后，决定登记、风险清单、验收契约、进度量定义与圈计划冻结。此后只有两种改动形式：**重新基线事件**（契约定义改一次、人口重跑、新计数成为新基线、`rebaselines` 加一，成员级已通过结论在定义未触及处保留）和**有界再入**（一轮再设计加一轮评审，见验收轮）。验收轮按共同原则 8 对非核心要求作出的取舍写入设计，不算改动冻结内容。原地改定义、边造边改验收口径、每圈重新发明通过标准都不允许。
6. **同类一次处理**：评审与验收的问题写明根因与检查范围，范围内全部同类由判定器列出并一次处理。同一「机制·模块」第二次出现时，消除该机制的结构性修改成为当前里程碑的完成条件（「缺陷复盘」第 4 条）。同类只在作用范围内认定（「缺陷复盘」第 8 条），不得以同类为由把范围外对象纳入本任务。
7. **竖切增量**：每个里程碑是可运行、可验收的系统状态。第一个里程碑消除风险清单上最高的一条（清单为空时只要求竖切），并在一个真实切片（一个变体、一个槽位、一个入口）上端到端跑通；先竖切，再扩人口。横向先建完一层再接下一层的计划不接受。
8. **协议版本固定与会话自主**：本次运行始终使用本文件中的规则，不得在运行中同步其它版本。立项、评审、工作、验收在独立会话中完成；各会话不向用户询问如何继续，遇到未规定事项依据任务目标、项目原则与已取得的证据作出决定并记录理由。Task 的核心目标不得放宽；其它编号要求只在不新增产品行为的前提下按原文不可达、与其它要求或项目权威规则冲突、或按测得的单位成本在硬上限内不可完成时，由评审轮（实现期由验收轮）以最小偏离取舍并写入设计（需要新增对象才可达的，按「评审条件」设计范围的两种情况判定）；未经测量的代价不是理由，测得的工作量是。

### 资源等待不结束轮次

本节适用于所有阶段，先于计数、结束和启动下一 session 的步骤执行，最后一圈也不例外。本轮必需验证因执行资源暂不可用而未运行或中断时，必须在当前 session 内使用等待工具等待，资源可用后继续执行；不得因等待结束 session、增加 `d` 或 `c`、启动下一 session，或判定任务失败。

优先使用项目已有的排队机制，遵守资源准入规则。等待工具单次返回或排队命令超时不代表等待结束：检查原进程，仍在排队或运行则继续等待，已因排队超时退出则在同一 session 重新排队，避免重复启动。没有排队入口时，用等待工具分段等待并复查准入条件。资源恢复后复核代码与环境，补跑缺失或已失效的验证；实际执行后发现的失败按原缺陷协议处理。

只有用户明确停止或宿主强制中断时，才在已有 `retro.md` 保存当前轮、已完成工作、等待资源、进程与待执行命令，不自动交接；恢复后核对状态并继续同一轮。不得自设等待时限作为中断理由。已证实的其它技术或权限问题仍按原取舍与终止规则处理。

### 文件与状态

本次运行只要求以下流程文件：

- 设计文档：`{{DOC_DIR}}/{{SLUG}}.md`
- 评审账本：`{{DOC_DIR}}/{{SLUG}}-review.md`，跨轮追加，不覆盖。
- 验收记录：`{{DOC_DIR}}/{{SLUG}}-acceptance.md`，每圈覆盖，保留四个常设段落（见验收轮）。
- 运行记录：`{{DOC_DIR}}/retro.md`，每轮追加一行，终止时补充总结。
- 证据目录：`{{DOC_DIR}}/evidence/`。设计快照在 `design-d<d>/`，每圈的运行输出在 `cycle-<c>/`。
- 可执行参考：`{{DOC_DIR}}/reference/`。

设计文档开头维护状态头，字段与取值固定：

```text
status: 立项中 | 实现中 | 已完成 | 不可实现 | 协议失败
design-round: d/3
cycle: c/C
current-milestone: M-xx
milestones: <已完成数>/<总数>
risks: <已退休数>/<总数>
progress: <进度量名>(<down|up>): v0, v1, ...
progress-step: <一圈至少改善多少才算进度>
no-progress-cycles: n
rebaselines: n
reentries: n
next-step: <验收轮接受的下一步；立项通过时由评审轮写 M-01 的第一步>
```

账目由 `{{RUNNER}}` 维护，各任务只调用它，不手改数字：

```bash
node {{RUNNER}} {{DOC_DIR}} state set <key> <value>      # 改一个状态头字段
node {{RUNNER}} {{DOC_DIR}} snapshot design-d<d>         # 改写设计前存快照
node {{RUNNER}} {{DOC_DIR}} diff design-d<d-1>           # 上一快照与当前设计的差异
node {{RUNNER}} {{DOC_DIR}} ledger add <id> <类别> <攻击对象> <后果或内容>
node {{RUNNER}} {{DOC_DIR}} ledger set <id> <open|closed|rebutted|note> [说明]
node {{RUNNER}} {{DOC_DIR}} progress append <value>      # 追加进度值并重算 no-progress-cycles
node {{RUNNER}} {{DOC_DIR}} progress rebaseline <value>  # 重新基线：新值成为比较基准，rebaselines 加一
node {{RUNNER}} {{DOC_DIR}} cycle advance                # c 加一，到达 C 时输出 CEILING
```

脚本不可用时，手工完成同样的更新并在 `retro.md` 记一行原因。

计数规则：

- `d` 由评审轮在结论为「需要修订」时增加；立项与再设计不增加。
- `c` 由验收轮在一圈结束时增加；一次有界再入计一圈。
- `C` 由立项按「设计文档要求」第 7 项推出并由评审核验，运行中不得提高。
- `no-progress-cycles` 由 `progress append` 按进度量方向自动计算；`progress rebaseline` 不计无进度。一圈的改善量不到 `progress-step` 不算进度。无进度阈值等于当前里程碑的估算圈数与 2 中的较大者；里程碑关闭时验收轮以下一里程碑进度量的初值重新基线，再入通过时评审轮把该计数清零。同一里程碑内重新基线最多两次，第三次起不再用 `progress rebaseline`，改用 `progress append`（按无进度计）。
- `next-step` 是下一圈工作的唯一权威；验收记录的「下一步要达成的结果」是它的展开，两者不一致时以 `next-step` 为准。

里程碑状态只有：`开放`（尚未完成）、`待审`（工作轮已取得通过证据，等待验收）、`已完成`（验收轮独立复验通过）。工作轮不得把里程碑标记为 `已完成`。

#### 缺陷复盘

验收确认的每个实现缺陷都按以下方法复盘。项目画像给出「缺陷复盘协议」（机制词表、逃逸类别细分、逃逸证明工具、主干既有缺陷的登记流程）时，使用项目画像中的词表与工具；没有给出时使用本节的默认词表和方法。每个里程碑维护 `reopen-count`（验收确认实现缺陷并把该里程碑从 `待审` 退回 `开放` 的次数；纯验证缺口、原本就是 `开放` 的里程碑不计）与 `defect-mechanisms`（以「根因机制·模块」为键的计数，验收每确认一个范围内的实现缺陷就为它的键加一，同一圈同一键只加一次，但一次同类普查命中两个以上实例时该键直接记 2；机制只能取词表，模块写项目的规范模块根，同一事实的多个副本分布在多个模块时记为一个键、模块写「跨模块」）。

1. **缺陷卡片**：每个实现缺陷在验收记录中写明现象、证据、根因机制与模块、在任务基线 revision 上能否复现、逃逸证明、逃逸类别、同类普查和补救。
2. **逃逸证明**：在缺陷修复前的代码上运行工作轮声称通过的验收命令，以及离缺陷最近的既有测试，记录结果属于哪一种：未执行、执行但看不到失败、失败但被忽略、不存在相关测试。
3. **逃逸类别与补救**：
   - **A 验证体系缺陷**：相关验证没有执行、被跳过、判定条件看不到失败，替身、夹具与真实实现不一致，或判定器定义缺少三部分之一而在信任基内静默放过。补救是修复验证机制本身（接线、取消跳过、修正判定条件并加正向对照、替换失真的替身、补全判定器定义），不只是增加一个用例；补全判定器定义按共同原则 5 作为重新基线事件记录。
   - **B 用例不足**：验证机制正常，但缺少维度或实例。补救是按共同原则 3 以判定器列出全部同类实例，并扩展模型、参考函数或输入生成器；只有确实没有可用模型时才补充单个用例，并写明理由。
   - **C 其他**：设计没有定义该行为、缺陷位于第三方或框架等。写明需要的设计再入或上游修复。
4. **完整复盘与结构性修改**：某个「机制·模块」计数达到 2 时，对它的全部缺陷执行逃逸证明与同类普查，并要求下一圈做出使该机制在结构上不能再发生的修改，例如一个事实只有一个写者或读者、从权威来源派生、类型化的载体、统一的参考函数；该修改是当前里程碑的完成条件。对同一事实存在多个副本、多个写者，或多处各自推导同一事实的机制，结构性修改必须使该事实只剩一个写者和一个推导位置；比较、校验或普查副本之间是否一致的检查属于验证补救，不算结构性修改。结构由工作轮设计，并同步修订设计文档中对应的决定。验收按三项验收：结构性质由判定器机检（类型、模块边界，或从权威来源列举全部写者与读者的契约测试），只识别已列出形式的检查不算；人为加回第二条路径或以未曾列出的写法加回时，测试变红；逃逸类别要求的验证补救已经完成。结构完成之前，同一机制的新实例照常认定为实现缺陷。只能靠语义判断的类别没有可机检的结构性质：结构性修改是在成员集合中删去副本或改为引用权威，验收按 Task 声明的抽样策略终止。同一里程碑 `reopen-count` 达到 3 时，对该里程碑出现过的每个机制执行完整复盘。
5. **验收只写要达成什么**：验收可以用候选修改验证可行性，但候选修改不属于下一步；工作轮自行设计实现，与验收的可行性验证不同时说明理由。
6. **主干既有缺陷**：在任务基线 revision 上能复现的缺陷不是本任务引入的。先按第 8 条判定作用范围：范围内的在本任务中修复，范围外的按第 8 条处理；两者都按项目画像的缺陷复盘协议登记，画像没有规定时在 `retro.md` 中单独列出。本任务引入的缺陷只记录在验收记录中。
7. **超出任务范围的修改**：结构性修改需要 Task 明确排除的改动时，按 C 类写明需要的再入或上游修复，并按项目的 issue 规则建立后续任务。该缺陷若违反 Task 要求或里程碑验收，里程碑仍不能关闭。
8. **作用范围**：验收对每个缺陷（包括记为备注但已复现、或有明确代码证据的偏离），以及里程碑验收报告的每个失败，判定它是否在当前里程碑的作用范围内，并在缺陷卡片中写明依据。
   - **对象**：缺陷所在的内容（代码、数据、文档或配置中出错的那部分）。以缺陷被发现时为准：修一处即可消除全部位置的，是同一根因，任一位置在范围内即整体在范围内；需要分别修改的多个位置，是同一机制的多个实例，逐个判定。
   - **范围内**，满足下列任一款：
     - (a) 缺陷使当前里程碑某条覆盖要求或结果所陈述的行为、取值或结构性质（例如「全部查表」「只有一个写者」）不成立；或者缺陷所在内容包含于这些要求或结果要求创建、修改或修复的对象之中（例如要求修改一条记录，则记录中的任一句）。只要求阅读、确认或报告的对象不因此进入范围，对其正确性的要求按行为判据判定。要求以文件路径指明对象的位置时，对象是该位置上被要求处理的部分，不是整个文件。结果要求创建的交付物（例如一个 PR）只纳入其中为实现该结果的内容。为说明依据、约束或排除而提及的对象不算；验收命令不扩大本款的对象。以类定义的对象（例如「同类写法」「每条红灯」）指判定器从权威来源列出的成员，卡片写明人口来源；无法枚举时按本款的行为判据判定。
     - (b) 缺陷由本任务的改动造成，在任务基线上不能复现（任一里程碑、任一圈）。
     - (c) 在缺陷被发现之前，本任务为实现当前里程碑的结果而新建或修改了缺陷所在的内容，包括为范围内对象编写的测试、检查器与证据。
   - **范围外**：不满足上述任何一款。为修复、登记或检查范围外缺陷而做的新建或修改（包括登记条目、证据，以及检查范围外对象的检查器）不使对象进入范围，这些内容上的缺陷与失败同样在范围外，不需要基线运行；其中由本任务造成的记在验收记录中，由项目画像的登记流程修正。本任务新建的检查器漏检时，按它漏检的对象判定；尚无实际漏检实例的形式缺口按下一款判定。
   - **同时服务范围内与范围外对象的内容**（例如检查器的人口同时包含两类对象，或一条登记条目同时登记两类缺陷）：按出错部分已经造成误判、漏判或误述的对象判定：涉及范围内对象的在范围内，其余在范围外；同一处错误同时涉及两类对象时按范围内。尚无实际漏检实例的形式缺口，只有范围内对象的现有内容含该形式时才在范围内。
   - **优先级**：(a) 优先于范围外一款的排除句；排除句优先于 (b)、(c)。
   - **归属与分配**：一个对象在多个里程碑的范围内时，结果有区分的，按缺陷违背的那句结果所属的里程碑；没有区分的，归其中尚未完成、编号最小的里程碑。已完成的里程碑不重新打开；归属于已完成里程碑的缺陷，归当前里程碑。范围内的缺陷可以分配给后续里程碑或独立 issue，条件是二者之一：该缺陷存在时，后续里程碑的结果陈述不能成立（只要求登记记录的句子不算）；或经负责人确认的变更作出该分配。验收写入设计文档的备注本身不是分配依据。原因未定位的失败同样适用本款。验收在卡片中写明分配及其依据；未分配的范围内缺陷是当前里程碑的完成条件。
   - **范围外缺陷的处理**：验收逐条写出核对过的要求编号与结果句子，以及不相符的理由；按项目画像的缺陷复盘协议登记（缺陷条目、仍失败检查的 owner 与期限、后续 issue）。它不成为本里程碑的完成条件，不计入 `reopen-count` 与 `defect-mechanisms`。登记不等于机制闭合：同一机制在范围内再出现时照常计数。
   - **验收中的失败**：里程碑验收报告的失败（包括结构性质的检查、整条测试 lane、全量测试、远端 CI 与退出码类判据）同样按本条判定。原因已定位到内容的失败按缺陷判定；竞态定位后按参与竞态的代码判定。以下各款只用于原因尚未定位的失败，其对象是失败的检查所检查的对象。基线是不含本任务任何改动的检出（优先当前主干；本任务的批次 PR 已合入主干时，或主干无法运行时，用任务基线 revision），在同一机器与同一配置上实际执行同一检查；本任务新建的检查叠加到基线检出上执行；合入了本任务提交的分支、代码阅读与 `git blame` 都不是基线运行。失败所在对象不在范围内时，验收取得基线运行结果：基线上出现一次即可停止并判为范围外；基线执行次数达到分支上的次数仍不出现的，才判为范围内。同样出现（包括间歇出现）的为范围外，按上一款登记，不阻断本里程碑，也不因「不得新增失败」或整体退出码成为完成条件；在取得基线结果之前，或基线上不出现的，该失败在范围内。环境失败指机器状态或外部服务造成、与本仓库代码无关的失败，须有证据：同一完整命令在采样证明空闲的机器上通过（focused 重跑不算），或错误直接指向机器状态或外部服务；只在负载或特定交错下出现的竞态是代码缺陷，按对象判定；单独重跑通过既不是基线运行，也不是环境证据；环境失败不是缺陷，在取得环境正常的运行结果之前，对应验收视为未执行。范围内的失败阻断验收，未分配时一直是完成条件；里程碑因此不能完成时置为 `开放`，但不计入 `reopen-count`，定位为实现缺陷后才计入。Task 要求对失败的处理另有规定时，以 Task 要求为准。
   - **无法判定时**：按本条仍无法判定的，按范围内处理，卡片写明无法判定的原因。
   - 除 (b) 款与失败的基线归因外，判定不看缺陷能否在任务基线上复现，也不看它与范围内缺陷是否属于同一机制。范围内且未分配的缺陷是当前里程碑的完成条件：不论能否在任务基线上复现，都在本任务中修复，计入 `defect-mechanisms`，里程碑为 `待审` 时计入 `reopen-count`。
   - 卡片的依据栏：(a) 写要求编号或结果句子，以及不成立的行为或包含它的对象；(b) 写引入它的提交或轮次；(c) 写新建或修改该内容的提交或轮次；分配写去向与依据；范围外写核对过的要求与结果及理由。

### 设计文档要求

设计文档是立项的产物，包含七部分，每部分只陈述当前结论，每个决定、事实或规则只在一处陈述，其它位置引用该处；过程写入 `retro.md`，实验输出放在 `evidence/`。再设计时改写对应段落，不在原文之后追加补充说明。

1. **背景与基线**：只写与任务有关的事实并给出代码、文档或运行证据；记录任务开始时的 Git revision、工作树状态与相关的已有测试结果。
2. **目标与完成定义**：逐项对应 Task 的核心目标与编号要求。每条核心目标指明它的验收契约（第 5 项）；涉及全体对象的编号要求写明确立方式，二选一：判定器（引用契约）或语义性质（引用 Task「价值判断」中的固定人口与抽样策略）。经评审或验收取舍的要求在该要求下写取舍后的口径、理由与证据位置。完成定义是：全部核心目标的契约通过，全部风险退休，全部里程碑 `已完成`。
3. **决定登记**：只保留一个明确方案，拆成编号决定 `D-01..D-n`。每条写结论、理由、证据位置、被否的替代方案，以及若它错了的返工后果（重做哪个里程碑、改哪个接口、哪个不可逆操作）。被驳回过的异议在该决定下记一行结论，再次提出须有新证据。
4. **风险清单**：编号 `R-01..R-n`，立项通过后冻结。每条写：不确定的量、依赖它的决定、消除方式。消除方式二选一：本轮用运行真实代码路径的最小验证实验退休，写结果与证据位置；或在某个里程碑用造的方式消除，写该里程碑编号、每种结果下预先决定的分支与触发条件；触发条件写成机读计数（判定器输出的字段与阈值），不写需要判断的描述。按返工检验（共同原则 4）属于立项期义务的风险必须在立项期退休。立项通过后只有某条决定被证伪时才能新增风险。
5. **验收契约**：每条核心目标一份。字段固定：人口的权威来源；信任基（接受而不证明的前提）；未知即失败；残余容忍（从 Task「价值判断」抄录，不得自定）；资格化方式（判别力作为全称性质时，变异算子集从权威来源派生并全量统计检出比例，自选注入不能代替）；一次真实切片上的运行：通过、失败、未知的计数，失败与未知清单位置，单位成本（由实际处理一个样本测得，不得估计），该切片在立项会话内实际处理的成员数（处理指使成员得到最终结论：修复后通过，或作出记录的裁定；判定器扫过不算处理）。Task 准入分类为 A 类时，契约是既有测试、旅程与门禁的命令清单及其预期结果；为 C 类时，契约写固定人口、抽样策略、吞吐预算与裁定记录的位置，真实切片运行指对不少于抽样样本量的成员作出记录的裁定；C 类契约通过的定义是：全部成员有记录的裁定结论，且按 Task 抽样策略抽出的一次全样本复核无错误。
6. **圈计划**：里程碑 `M-01..M-N` 按依赖顺序编号。每个里程碑写：可独立观察的结果；覆盖的 Task 要求编号；前置里程碑；验收命令（尚不存在时准确说明需要新增的测试或运行入口）；它退休的风险编号（若有）；它推进的进度量；估算圈数及推导；`reopen-count: 0`、`defect-mechanisms: {}`；最新证据。第一个里程碑必须是竖切片并退休风险清单上最高的一条（共同原则 7）。进度量按准入分类固定一个：A 类为已完成里程碑数（up），Task 价值判断定义了有效样本时可改为累计有效绿样本数（up），不用失败项数（间歇失败会振荡）；B 类为契约判定器的失败加未知计数（down）；C 类为已裁定成员数（up）。判定器尚未建成的里程碑临时取该里程碑验收命令的失败项数（down），判定器建成后以首次运行计数重新基线。进度步长 `progress-step` 随之固定：有人口的里程碑为 `ceil(立项切片实际处理的成员数 ÷ 2)`，没有人口的为 1；一圈的改善量不到步长不算进度。
7. **硬上限**：`C` 等于各里程碑估算圈数之和。有人口的里程碑：`估算圈数 = ceil(待处理成员数 ÷ 立项切片实际处理的成员数) × 2`，待处理成员数在 B 类是立项运行得到的失败加未知计数，在 C 类是固定人口的成员数；没有人口的里程碑取 3，含 PR 合并与回读的取 4；A 类里程碑一律按没有人口计，红灯、测试文件或样本组不是人口。乘数 2 与常数 3、4 是模板默认值，只能在模板中改，不在任务中改。写出每个里程碑的算式与所用实测数字；评审只核验算式使用了契约中实测的数字。

设计需要精确行为（分类、取值表、逐条规则、真值表）时，不用文字或表格承载，交给 `reference/` 下一个可执行参考（原型函数及其判别用例集，或最小契约测试）作为唯一权威，正文只陈述决定并引用它。参考自身的细节错误按实现缺陷处理。

写入设计的关键技术主张（按返工检验属于立项期义务的主张：某个接口、注入路径或观测量是否存在，某个迁移能否在既有数据上执行，某个判定器能否在真实人口上运行并对未知失败）由写入它的会话在同一轮用最小验证实验证明并引用实验输出。实验必须运行真实代码路径（导入生产函数、使用生产 schema 或 DDL，或在真实环境中执行）；手工转写源码逻辑的模型不算。实验不属于重型任务，不以负载或时长推迟；确实无法执行时该主张不写入设计，改用能够验证的方案。关于全体对象的主张不由实验证明，由契约的运行计数陈述。

### 评审条件

评审只审决定登记、风险清单、验收契约与圈计划，不审文档是否写到了实现细节。

**通过**的四个条件，全部满足即通过，与评审是否还有意见无关：

1. 决定登记中没有未反驳的阻塞问题。
2. 每条核心目标有验收契约，字段齐全，残余容忍与 Task「价值判断」一致。
3. 每份契约在真实切片上运行过一次，有计数与测得的单位成本；`C` 的推导使用这些数字。
4. 风险清单中每条风险有消除方式，按返工检验属于立项期义务的已退休；第一个里程碑是竖切片。

**阻塞问题**必须同时写明两项，缺一项的是注意事项：它攻击的对象（某条 `D-n`、某份契约的某个字段、某条 `R-n`、某个里程碑的划分或顺序）；它的后果：按返工检验的四种返工之一，或某条核心目标不可达，或该决定与 Task 明文约束、项目权威规则冲突，或某条关键技术主张没有验证或验证不真实（没有运行真实代码路径、没有覆盖该主张、结果不支持结论）。

以下不是阻塞问题：判定器定义完整时某个成员未列出、信任基之外的写法、归类规则的细节；契约运行结果中的失败与未知；设计中已写明理由的取舍与范围判定（只有给出理由不成立的新证据时才重开）；本轮未改动且已有结论的决定。注意事项记入账本（类别 `note`），不阻塞，不写入设计，实现期由验收发现。

**转换规则**：分析不能解决的阻塞问题由再设计转为风险清单的一条，写明消除它的里程碑、分支与触发条件；转换后该问题闭合。这不是推迟：推迟是不处理，转换是预先定好用什么证据、在哪一圈、走哪条分支解决。按返工检验属于立项期义务的问题不得转换。

**设计范围**以 Task 的编号要求和其它明文约束为界。修正范围内对象的事实错误、矛盾、可执行性与可验证性不算扩大范围。只有两种情况可以把新对象纳入设计：缺少它会直接使某条 Task 要求的验收条件或 Task 写明的目的不能达成（写明要求编号与失败方式）；范围内对象改为判定器的人口，由此列出的成员随之纳入（只改变表达方式，不纳入新类别）。范围外的发现记入账本（类别 `out-of-scope`），由再设计按「缺陷复盘」第 8 条登记，不写入设计。
