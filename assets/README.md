# 协议模板维护说明

`protocol-template.md` 是新生成循环任务的模板来源。每个任务文件都会包含生成时的模板全文和模板哈希；运行开始后不得同步其它版本。

## 当前设计

循环是一个螺旋，没有独立的设计阶段。任务文件结构为：共享规范 → `任务`（正文：背景、核心目标、编号要求、准入分类、价值判断）→ `立项`（兼再设计）→ `评审` → `工作轮` → `验收轮`。启动句直接写任务段名，例如 `Please execute docs/<slug>/<slug>-task.md 验收轮.`。两个角色：作者（Task 1、工作轮）与独立判定者（评审、验收）。每步末尾直白写明下一步启动谁；评审与验收中的分支写成按顺序命中的执行句。

生成期是唯一有人的时刻。SKILL 第 3 步对每条核心目标问「有没有现成的外部可执行判定器」，分 A（有）、B（全称性质无判定器，判定器优先）、C（语义人口，必须声明抽样策略与吞吐预算）三类，并把残余容忍、付费口径、范围、降级分支写进 Task 的「价值判断」节；写不出来不生成。

立项产出七部分：背景与基线、目标与完成定义、决定登记（含若错的返工后果）、冻结的风险清单（每条风险要么本轮实验退休，要么写明在哪个里程碑用造的方式消除与预定分支）、每条核心目标的验收契约（人口来源、信任基、未知即失败、残余容忍、资格化方式、一次真实切片运行的计数与单位成本）、竖切的圈计划、由实测单位成本推出的硬上限。评审按四个产物状态条件判通过，与是否还有意见无关；阻塞问题必须写攻击对象与返工后果，缺一项是注意事项；分析不能解决的阻塞问题由再设计转为带分支的风险；立项最多三轮，三轮不闭合是 Task 定义的问题。账本跨轮追加，评审先 diff 快照核验自己上一轮问题的处置。

实现期每圈一个工作轮加一个验收轮。工作轮执行验收接受的下一步并带证据提案下一步；验收轮复验、把每个反例先交判定器（失败或未知是未完成工作，信任基内静默放过是重新基线事件，信任基外是残余）、判增量、判提案、判进度。进度量按准入分类固定一个（A 已完成里程碑数，或 Task 定义的累计有效绿样本数；B 失败加未知计数；C 已裁定成员数），并带由实测推出的进度步长，由验收轮自己复跑取值。停止规则：无进度圈数达到阈值（A 类里程碑为其估算圈数，B、C 类为 3；一圈改善不到进度步长不算进度）走风险清单的预定分支或有界再入（一轮再设计加一轮评审，计一圈）；再入后再次达到阈值以不可实现终止；到达硬上限（`ceil(待处理成员数 ÷ 立项切片实际处理的成员数) × 2`，无人口里程碑取 3、含 PR 合并与回读的取 4，求和）以协议失败终止。

账目由 `assets/cycle.mjs`（ensure 为仓库 `prompt/skill/cycle.mjs`）维护：状态头、快照与 diff、账本行、进度序列与无进度计数、圈计数。提示词只调用它，不做算术。

当前模板保留：可选的队列终止句；独立会话之间的角色分工；「资源等待不结束轮次」；缺陷复盘（缺陷卡片、逃逸证明、逃逸类别 A/B/C、第 8 条作用范围、默认机制词表）；同一「机制·模块」第二次出现时结构性修改成为完成条件、同一里程碑第三次 reopen 时完整复盘；验证缺口加强后立即复验不退回；验收只写要达成什么；关键技术主张同轮最小实验；精确行为进可执行参考；设计只陈述当前结论。

当前模板不再统一要求：独立的设计裁决座位；15 轮设计预算；`N = 5 × 里程碑数` 的实现预算；`convergence-mode` 与四段式 `Convergence Note`（验收记录改为四个常设段落）；评审文件每轮覆盖；关于同类、闭合、信任基的长条款（改为契约表单的字段）；以及更早废弃的规范性条款编号体系、条款交互矩阵、裁决索引、通用断言库、人工白名单、单个里程碑预算与人工续跑菜单。

## 维护要求

1. 使用多个任务的可核对复盘证据评估模板，不因单个任务增加全局规则。
2. 优先删除无助于产品推进的流程要求。
3. 新规则必须说明它防止的具体失败，并说明为何不能由项目原有测试或角色职责解决。
4. 模板使用正式、准确、容易理解的语言；任务接力必须直白可执行。
5. 修改模板后更新 Git 提交；任务文件中的模板哈希用于识别运行版本。

## 2026-07-31 重构

本次版本根据 mesh table、mesh elastic scaling 和 mesh scale switch wiring 多次运行的复盘进行重写。历史记录显示：

- 设计失败主要来自验证要求不断扩展、覆盖流程过重和协议版本中途变更。
- 最有效的机制是实际代码验证、同类问题一次检查、有限行为使用表或参考函数表达，以及实现审计加强验证后立即复验。
- 实现预算应在里程碑之间共享；切换类里程碑可能使用超过五轮，但完整任务仍可能在 `5 × 里程碑数` 内完成。

因此本版本把 skill 恢复为任务编排模板，项目特定的验证模型由具体任务按需要建立。

## 2026-08-04 循环写法回退

把任务之间如何接力的写法换回归档任务常用的顺序任务体：共享规范在前，`Task 1` / `additional task 1–4` 依次列出，每步末尾写清启动目标。六类复审、共享预算、reopen/收敛等新内容保留不动。

## 2026-08-24 队列终止接力

串行大任务不再使用独立监督 session 做定时轮询。循环任务在 additional task 2 与 additional task 4 的终止出口执行生成时写死的 `{{ON_TERMINATE}}`。有队列时启动队列文档；无队列时保持「终止，不启动新的 chat」。

## 2026-08-30 按任务指定会话后端与启动参数

启动句中的单一 `{{SESSION_SKILL}}` 按目标任务拆分为 `{{SESSION_SKILL_REVIEW}}` / `{{SESSION_SKILL_ADJUDICATE}}` / `{{SESSION_SKILL_IMPL}}` / `{{SESSION_SKILL_AUDIT}}`，并在每个启动出口增加 `{{SESSION_ARGS_*}}` 启动参数后缀（无参数时为空字符串；有参数时为「，启动参数：`<flags>`」）。设计评审与实现各有两处启动出口，同名占位符全局同值。队列终止句同样在生成时写死队列接力后端与参数。旧任务文件继续使用生成时的模板快照，不受影响。

## 2026-10-12 第二次补充：开放类别只审识别机制，实现注意事项不写入设计

依据：issue-1542 第 2 次运行（模板 `7fd9e49c484b`）。前 6 轮评审的阻塞问题数为 6、5、4、3、4、2，裁决全部采纳（24/24），没有一轮归零。

- **开放类别只审识别机制**：防止的失败是「评审每轮找出一个未列出的成员，裁决补列该成员，下一轮再找出下一个」。该运行的核心目标要求「注入任一第二个读者或写者后合同变红」，对象无法逐个列尽；读写者完备性在 6 轮中出现 5 轮（d1 R2/R5、d2 N2、d4 Q-1/Q-2、d5 R-2、第 6 轮评审 R-2）。每次以补列表回应（d4 补字符串扫描方法、d2 补命名再导出），下一轮评审即找到列表外的形式；G1 在 d5 改为对闭包内全部检视语法节点计数后不再复发，G3 仍按列出的形式求值，第 6 轮评审又找到 `export *`、`new URL(…, import.meta.url)` 与条件表达式三种。第 1 次运行中同一领域复发 7 轮。另见上节：5 个高轮次循环的阻塞问题引用「列全」「同类」类开放普查要求。原判据 3 已写明「清单缺少某种形式本身不构成盲区」，但缺少的成员可以改按判据 1 提出（「不能达成编号要求」），护栏被绕开；第 6 轮评审的 R-2 即如此。项目测试与审计角色无法解决：问题发生在设计循环内，出口条件要求一轮零采纳。改为：开放类别的设计决定是识别机制是否报告未识别成员；已报告时缺少某个成员是实现细节，不论按哪条判据提出；未报告时修正机制而不补列形式。
- **实现注意事项不写入设计**：消除协议内部的矛盾。原文要求注意事项「保留在评审文件中」，而评审文件每轮覆盖，注意事项必然丢失，于是裁决轮把注意事项写进设计（该运行 d2–d5 约 21 条，例如 d4 一轮 9 条），写进去的内容成为下一轮评审的对象：d3 写入的「句子级锚点」成为第 6 轮评审的阻塞问题 R-1（与协议合同 3f 的短语级定义冲突）。按实现细节的定义，注意事项由实现期的验收与审计发现，不需要保留，因此改为只写在评审文件中、不写入设计；设计中被注意事项指出的事实错误可以改正或删去，但不因此新增规则。证据强度：在 Mesh `origin/main` 的 130 个循环的 retro 中，裁决写入注意事项的记录很少，与设计轮数没有相关（这类记录多出现在通过轮）；确认的因果只有上述一例。本项作为消除矛盾的改写保留，不作为预期缩短轮数的依据。
